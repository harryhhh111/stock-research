# Coding Agent 推理负载：日内峰谷、峰时价格与全球时区分布

**整理日期**：2026-09-02
**用途**：修正 `coding 需求模型.md`（统一版）中"86400 秒均匀负载"的假设，提供峰谷系数 1.3–1.8 的依据
**信息标注约定**：【一手】官方/论文数据；【二手】媒体转述；【自算】本文复算值

---

## TL;DR

1. **Coding 推理负载的日内峰谷是真实存在且很大的**：生产环境 code 服务峰值约为平均值的 **3.3 倍**（Azure trace），GitHub Copilot agent 实测白天峰值约为夜间基线的 **4–5 倍**。【一手】
2. **全球聚合后峰谷被时区摊平，但摊不平**：按开发者时区分布自算，全球需求峰值/平均 ≈ **1.57**，且 **约 63% 的日需求落在美国白天的 12 小时窗口内**（13:00–01:00 UTC）。【自算】
3. **市场信号直接证实美国白天是瓶颈**：Anthropic 从 2026 年 3 月起在**工作日太平洋时间 5–11 AM**（= 美东上午 + 欧洲下午的全球重叠峰）削减 Claude Code 5 小时限额，约 7% 用户开始撞顶。【二手】
4. **峰时电力成本信号**：PJM 容量价格因数据中心需求从 $28.92 → $329.17/MW-day（10 倍）；ERCOT 夏季峰时实时价 $100–300/MWh，极端到 $1,000+。【一手/二手】
5. **对模型的修正方向**：均匀负载假设下算出的是**平均功率（能源口径）**；若问"要建多少 GW（容量口径）"，需在平均功率上乘 **1.3–1.8 倍的峰谷系数**（取决于负载可平移程度）。Batch API 五折、夜间调度 agent 是天然的削峰手段。

## 1. 日内峰谷：推理负载到底有多不均匀？

### 1.1 Azure 生产 trace（目前最权威的公开数据）

Microsoft Azure 公开的 LLM 推理 trace 被多篇论文分析，结论一致：【一手】

- **Code 服务峰值 prompt TPS 是平均值的 3.3 倍，是最低值的 35.6 倍**；工作日规律明显，夜间和周末下降。峰值出现在**下午和傍晚**。([PreServe, arXiv:2504.03702](https://arxiv.org/html/2504.03702v2 "citation"))
- Code 请求的 prefill 吞吐呈显著日内模式（下午/傍晚达峰），而 conversation 请求全天相对平稳——即 **coding 负载比 chat 更"白天化"**。([VoltanaLLM, arXiv:2509.04827](https://arxiv.org/html/2509.04827v3 "citation"))
- 各工作日峰值幅度本身还有 ±35% 的不可预测波动，意味着按平均峰值 provisioning 仍会周期性欠配。

### 1.2 GitHub Copilot coding agent 实测（2026 年 6 月，一周数据）【一手】

论文 *Agentic Coding in the Wild*（arXiv:2608.00101）对生产环境 Copilot agent 会话做了一周采样：([arXiv](https://arxiv.org/html/2608.00101v1 "citation"))

- 会话数、LLM 调用、token 量高度同步，**白天峰值 ≈ 夜间基线的 4–5 倍**，夜间和周末显著下降。
- 波动主要由**中等长度 prompt**驱动；超长 prompt（重度 agent 会话）全天相对稳定 → 重度 agent 负载天然更平。
- **Median turn = 160.2K prompt tokens / 265 completion tokens**；P90 turn > 1M prompt tokens。这直接验证了需求模型第二版"cached input 占绝对大头"的 token 构成假设（output 只占总 token 的 ~0.2%）。
- 周末会话更少但更重：工作日每会话 1.2–1.7M prompt tokens，周末 1.9–2.4M。

### 1.3 重要的反直觉修正：设施级聚合会大幅摊平峰值

一篇 2026 年的基础设施规划论文把 Azure 生产 trace 驱动到 240 台服务器的数据大厅模型里（每台服务器请求流加随机时间偏移、去相关），结果是：【一手】([arXiv:2603.18383](https://arxiv.org/html/2603.18383v1 "citation"))

- **设施级 peak-to-average 只有 1.19，负载因子 0.84**。
- 单服务 3.3× 的峰谷，在大规模多租户聚合后被平滑掉大部分。

**含义**：峰谷系数取决于观察尺度——单个企业/单服务是 3× 以上；超大规模多租户云是 1.2× 左右；**全球单一用途（coding）跨时区聚合介于两者之间**，这正是第 3 节要算的。

## 2. 峰时定价：市场如何给"美国白天的算力"定价

### 2.1 推理 API 侧：分时定价已经以"延迟折扣"形式存在【一手】

| 机制 | 折扣 | 实质 |
|---|---|---|
| OpenAI / Anthropic / Google / Mistral Batch API | **50%** | 24 小时内异步完成，等于把负载让渡到闲时 |
| Anthropic 缓存读取 | 90%（$0.2/M vs $2/M） | 摊薄重复 context 成本 |
| Anthropic Claude Code 峰时限流 | — | **工作日 5–11 AM PT 削减 5 小时窗口限额**，2026 年 3 月起，约 7% 用户开始撞顶 |

Batch 五折 + 峰时限流两件事合起来是非常清晰的市场证据：**提供商的高峰实时容量是稀缺资源，闲时容量过剩**。Anthropic 的限流窗口（太平洋时间早上 5–11 点）精确对应"美东上午 + 欧洲下午"的全球需求重叠峰。([TrueFoundry](https://www.truefoundry.com/blog/claude-code-limits-explained "citation"), [implicator.ai](https://www.implicator.ai/anthropic-shifts-enterprise-billing-to-per-token-pricing-the-flat-fee-era-is-over/ "citation"))

### 2.2 电力侧：峰时价格信号【一手/二手】

- **容量市场（最直接的稀缺定价）**：PJM 容量价格从 2024/25 的 **$28.92/MW-day** 涨到 2026/27 的 **$329.17/MW-day**，约 10 倍，IEEFA 明确归因于数据中心负荷预测。([IEEFA](https://ieefa.org/resources/projected-data-center-growth-spurs-pjm-capacity-prices-factor-10 "citation")) 折算：$329/MW-day ≈ **$13.7/MWh 的容量成本摊到每一度电**（$329×365÷8760h）——这还没算电能量本身。
- **电能量市场峰谷价差**：ERCOT 夏季峰时（HE18–HE22 傍晚）实时价常见 **$100–300/MWh**，拥塞时可瞬时到 $1,000/MWh；CAISO 傍晚峰 $70–100+/MWh，而正午光伏大发时**经常为负电价**。([Ascend Analytics 市场周报](https://www.ascendanalytics.com/blog/bid-optimization-ercot-caiso-market-outlook---week-of-august-27th-2025 "citation"), [Constellation](https://www.constellation.com/solutions/for-your-commercial-business/energy-tools-and-resources/energy-market-update.html "citation"))
- **Coding 需求峰（下午）与电网峰（傍晚）部分错开**：美国下午时段夏季有光伏支撑，电价压力小于傍晚；但 PJM（弗吉尼亚数据中心走廊）光伏渗透率低于 CAISO，下午峰仍偏贵。
- **7×24 稳定供电的真实成本**：McKinsey 估算 24/7 绿电 PPA（风+光+锂电）在多数地区 **>$200/MWh**；核电 PPA 约 $80–120/MWh 固定 20–40 年。([McKinsey](https://www.mckinsey.com/industries/electric-power-and-natural-gas/our-insights/how-hyperscalers-are-fueling-the-race-for-24-7-clean-power "citation"), [SMR Pillar Guide](https://howtostoreelectricity.com/nuclear-smr-ai-data-centres/ "citation"))

**含义**：coding 负载的"白天化"对电网其实是**好坏参半**——比 7×24 满负荷训练更贴合光伏曲线，但峰谷波动本身推高容量成本（PJM 已经在定价这一点）。

## 3. 全球用量的时区分布：美国白天之外还剩多少？

### 3.1 用量地理分布【一手】

**Claude（Anthropic Economic Index，2026 年 1 月报告）**：([Anthropic](https://www.anthropic.com/research/economic-index-march-2026-report "citation"), [The Hindu BusinessLine](https://www.thehindubusinessline.com/info-tech/software-development-drives-claudeai-adoption-in-india/article70515245.ece "citation"))

- 总用量前五：**美国、印度、日本、英国、韩国**；前 20 国占人均调整后用量的 48%。
- 印度总用量全球第二，且 **45% 集中在计算机/数学类任务**（全球最重 coding 的大国）。

**GitHub 开发者（Octoverse 2025，coding 需求的最佳代理）**：([GitHub Blog](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/ "citation"))

- 开发者数：美国 ~28M、印度 ~21.9M、巴西 ~6.9M；印度预计 2030 年达 57.5M（超过美国）。
- **GenAI SDK 仓库贡献：美国 31.8%、印度 12.5%**，第二梯队（德/日/英/韩/加/巴/西/法）合计约 40%。
- 人均贡献强度美国仍显著更高（贡献量第一但开发者数与印度接近）。

**ChatGPT（消费级参照，2026 年初）**：([Siana](https://www.sianamarketing.com/resources/chatgpt-usage-by-country-2026 "citation"), [Omnibound](https://www.omnibound.ai/blog/chatgpt-user-statistics "citation"))【二手】

- 美国流量份额仅 ~15–17%；亚太 28.6%、北美 19.8%、欧洲 14%。消费级比 coding 更分散。

### 3.2 自算：全球 coding 需求的 UTC 日内分布【自算】

方法：以 GitHub GenAI 贡献份额做地区权重（US 31.8%、India 12.5%、加拿大 5%、巴西/拉美 7%、西欧 9%、中欧 9%、日韩 10%、其余 15.7% 按全球均匀处理），各地区需求在其本地工作时段（约 9–19 点）内均匀分布，叠加到 UTC 24 小时：

```
UTC 时刻 | 全球需求份额
00:00    4.09%   ← 美西傍晚
01–03    ~1.5%   ← 全球低谷（美国深夜、亚洲清晨前）
04–07    ~2.8%   ← 印度上班
08:00    3.65%   ← 欧洲陆续上班
09–11    4.53%   ← 欧洲+印度
14–17    6.54%   ← ★ 全球峰: 美东上午+美西清晨+欧洲下午+印度傍晚
18:00    5.66%
19–21    4.78%   ← 美国下午
22–23    4.09%
```

**结果**：

| 指标 | 数值 |
|---|---|
| 全球峰值/平均（小时级） | **≈ 1.57** |
| 美国白天窗口（13:00–01:00 UTC，美东 9:00–21:00）集中需求 | **≈ 63%** |
| 核心重叠峰（14:00–18:00 UTC，美东上午+欧洲下午） | **4 小时占 26%** |

**交叉验证 ✅**：自算峰值窗口 14:00–18:00 UTC = 太平洋时间 7–11 AM（夏令时），与 Anthropic 实际限流窗口 5–11 AM PT 高度重叠。两个完全独立的方法指向同一个结论。

### 3.3 结论口径

- **"大部分算力要在美国白天提供"基本属实，但要打折**：不是 80–90%，而是 **~60–65% 落在美东 9 点–晚 9 点的 12 小时窗口**；真正的尖锐峰是美东上午+欧洲下午重叠的 4–6 小时（占 ~26–32%）。
- **亚洲（印度+东亚 ~22–25% 需求）和欧洲（~18%）贡献了天然的"跨时区削峰"**：它们的白天填进了美国的夜间。如果美国单独建产能服务全球，美国凌晨（全球低谷 ~1.5%/h）产能利用率只有峰值的 ~1/4。
- **趋势方向是更分散而非更集中**：GitHub 新增开发者每分钟 APAC ~25 人 vs 欧洲 ~12 人；印度开发者 2030 年将超美国。5 年后美国白天窗口的集中度大概率降到 55–60%。

## 4. 对需求模型的修正建议

原模型 `Power(MW) ≈ 12.4 × 用户(百万) × Token(百万)` 用 86400 秒均匀折算，算出来的是**平均功率**。要回答"需要建多少 GW 数据中心"，建议拆成两个口径：

| 口径 | 公式修正 | 基准情景（1000 万重度 DAU） |
|---|---|---|
| **能源口径**（年耗电量、电网能量平衡） | 不变 | 0.6 GW 平均 ≈ 5.2 TWh/年 |
| **容量口径**（要建多少 GW、多少机柜） | × 峰谷系数 | **0.8–1.1 GW** |

峰谷系数取 **1.3–1.8** 的依据：

- 全球聚合自算 1.57（小时级小时均值）→ 中枢 ~1.5；
- 向下修正：设施级多租户聚合可摊到 1.19；Batch API 五折、夜间定时 agent、周末重度会话都在把负载往闲时搬；
- 向上修正：日峰值本身 ±35% 波动（Azure trace）、周末工作日差异（工作日高）、若产能区域性部署（如主力在弗吉尼亚/德州）则享受不到全球时区摊平，回到 2–3×；
- 若未来 agent 夜间自主运行比例大幅上升（"晚上继续跑"的情景），系数会趋势性下降——这是供给侧最希望看到的。

**一句话**：原模型的 GW 数当"平均负载/能源账"用是对的；当"装机需求"用要加 ~50% 裕量，再叠加电网侧容量成本上升（PJM 式 10 倍容量价格）对度电成本的传导。

## 5. 信息质量与未决问题

- Azure trace 是 2024 年的 chat/code 分类服务，未必完全代表 2026 年 agentic 长会话；GitHub Copilot 论文（2026 年 6 月数据）是目前最贴近的一手来源。
- 自算时区模型的地区权重来自 GenAI SDK 贡献份额，不等于 coding agent 付费 DAU 分布（美国付费渗透率显著更高，可能让美国权重再上移 5–10 pp）。
- 未获得：Anthropic/OpenAI 官方公布的分时负载曲线（不存在公开数据）；OpenRouter 有公开排名但无分时段数据。
- ChatGPT 地理分布数据来自 Similarweb 第三方流量估计【二手】，精度有限，仅作消费级参照，未用于模型。
