# AI 训练数据供应商的招聘画像：过去 12 个月究竟在招什么人

> 整理日期：2026-09-15  
> 观察区间：2025-09-15 至 2026-09-15  
> 研究对象：Scale AI、Surge AI、Mercor、Handshake  
> 研究问题：过去一年，这些公司公开招聘反映了什么能力建设？这些岗位是否就是“程序员”？

---

## 结论先行

**是，环境、评测和 Agent 平台这一层，招的确实主要是资深软件工程师、研究工程师和研究科学家；但这不是整张招聘图。**过去一年的可见人才结构由五层共同构成：

1. **环境系统工程**：容器/沙盒、编排、状态重置、轨迹采集、验证器（verifier）、可观测性。这是程序员的岗位，且往往要求分布式系统、Docker/VM/Kubernetes、后端平台或全栈能力。
2. **任务与评测研发**：把真实工作拆成任务、rubric、奖励函数与反作弊检查；招聘对象是研究工程师、ML 研究员、评测研究员与领域任务设计者。
3. **专家供给和质量运营**：筛选、培训、匹配和复核医生、律师、金融从业者、SWE 等外部专家。这里既有内部项目/运营岗，也有大量合同制、按项目结算的专家岗位。
4. **真实数据取得与企业落地**：数据合作、数据 acquisition、Forward Deployed Engineer（FDE）、客户部署和隐私/法务。这说明供应商不只生产通用题库，也在争取企业的真实工作流和操作数据。
5. **安全与对抗测试**：red team、政策训练、安全评估、产品/数据合规。它们是进入真实企业环境时必要的质量与风险控制，不应自动算成 cyber 训练数据采购。

因此，较严谨的表述应是：**公开招聘最清楚地显示，训练数据供应商正在把“人类专家 + 任务”工业化为“可运行环境 + 可验证轨迹 + 企业部署”的生产系统。**它不能证明 coding 占所有模型训练预算的最大份额，也不能从职位数推出任何一家公司的真实雇员数、已招人数、数据产量或客户订单金额。

## 一、研究边界：这是公开招聘画像，不是完整的全年招聘台账

### 1.1 为什么不能直接回答“过去一年一共招了多少人”

四家公司都没有披露可审计的月度 headcount、offer、入职或离职数据。公开 ATS（Greenhouse/Ashby）通常只展示**当前仍开放**的职位；关闭的职位、是否最终录用、录用人数、候选人来源和实际到岗时间大多不可见。职位页上的 `datePosted` 也只说明职位公开的日期，不等于实际入职日期。

Scale 的 Greenhouse API 还会给出职位的 `updated_at`，但这只是最后一次页面更新，不能当作最初发布时间。2026-09-15 的快照中，Scale 有 228 个开放职位；按标题机械匹配 `RL / Agent / Environment / Evaluation / Frontier / Code / Data Acquisition` 得到 43 个匹配项，其中 16 个属于 Human Frontier Collective（Fellow 项目）。这个数字用来展示**职位板的构成**，不是过去一年的净招聘数，也不是 43 名工程师。[^1]

Handshake 的职业页同时搜索“Careers at Handshake”和“AI Trainer”机会，展示 64 个职位；其页面将原有职业网络、企业 AI 工程和 AI 训练项目混在同一入口。故 64 既不是 AI 数据团队人数，也不是 12 个月新增人数。[^2]

**本报告的证据分级：**

| 证据级别 | 含义 | 在本文中能支持什么 | 不能支持什么 |
|---|---|---|---|
| A：带 `datePosted` 的仍开放职位 | 可确认某一日期时该职位对外招聘 | 具体人才类型在过去一年被公开寻求 | 已经招到多少人、职位持续多久 |
| B：带发布日期的公司文章/项目说明 | 可确认公司在该时点公开陈述的产品方向 | 组织为何需要某类人才 | 客户采购额、行业总投入 |
| C：2026-09-15 当前职位快照 | 可确认研究日仍在招什么 | 当前组织能力布局 | 过去一年完整的时间序列 |
| D：LinkedIn 区间/员工档案 | 宽口径组织规模线索 | 正式团队的大致数量级 | FTE 精确数、专家网络活跃人数 |

### 1.2 人员类型必须先拆开

| 人员类型 | 典型职位 | 是否是公司正式员工 | 对“数据供给”的含义 |
|---|---|---|---|
| FTE 工程/研究 | Staff SWE、Research Engineer、ML Scientist、PM | 通常是 | 建造可复用的环境、训练/评测和交付底座 |
| FTE 运营/商业/法务 | Delivery Ops、Data Partnerships、FDE、Commercial Counsel | 通常是 | 获得数据、管理专家、把项目落地到客户 |
| 合同制领域专家 | Senior SWE for coding RL、法律/医疗/金融 consultant | 不一定；常为独立承包商 | 将真实工作经验转为任务、样例、rubric 或审核 |
| 项目制 trainer / Fellow | AI Trainer、Human Frontier Collective Fellow | 不是传统意义 FTE；工时未保证 | 弹性供给漏斗，不能与员工数相加 |

Handshake 的帮助中心明确说明其 AI Trainer 是按项目工作的独立承包商、并不保证工时；Surge 的 agentic-coding 环境岗位也明确是 remote contract/project work。[^3][^4] 这正是过去一年研究招聘时最容易犯的错误：把职位广告、Fellow 社区和正式工程组织混成一条“员工人数”曲线。

### 1.3 本文的技术口径：不要把“通用做法”误读为“某公司已逐项披露”

下文讨论 Coding Evaluation、RL 环境和 verifier 时，严格区分三种信息：

| 标签 | 证据来源 | 可以怎样写 | 不能怎样写 |
|---|---|---|---|
| **岗位原话** | 一家公司的职位描述 | “Scale 的该岗位写明要做 sandbox、版本、rollout、trajectory 与 verifier” | “所有供应商都用同一套系统” |
| **公开实现案例** | 开源 benchmark、论文、官方技术文章 | “以 SWE-bench 为例，真实 GitHub Issue 还要配代码库、测试和可运行评测 harness” | “Surge/Scale 对每个任务都采用 SWE-bench 的具体实现” |
| **本文归纳** | 将岗位原话与公开案例相连 | “一个稳健的 coding 任务生产流程通常需要任务筛选、可运行环境与验收” | “某公司必然做了隐藏测试、许可证核查或初始数据库状态等每一个环节” |

尤其应避免使用“只要收集 GitHub 仓库还不够，所以**必须**补齐 X、Y、Z”这种绝对说法。更准确的是：**若目标是得到可重复、可信、适合大规模 agent 评测或 RL 的 coding 任务，公开案例显示通常还需要对任务质量、运行环境和验收信号做额外工程化。**SWE-bench Verified 的实践显示，原始 GitHub Issue/PR 样本会因任务描述不清、测试不公平或环境搭建不可靠而需要人工筛选和容器化评测；这证明了“原始仓库不等于可靠评测任务”，但不证明任何特定供应商对全部项目采取完全相同的流程。[^18]

## 二、可追溯的时间线：能确认的不是“每月招了几人”，而是能力建设的节点

| 时间 | 公开记录 | 招聘/组织含义 | 证据级别 |
|---|---|---|---|
| 2025-11-03 | Surge 发布 RL 环境与企业任务研究，后于 2026-02-05 更新；文中把训练/评测从单轮回答转向多步骤工具任务作为核心变化 | 为其后续的 RL 环境架构、任务与评测招聘提供产品背景；不是招聘记录 | B |
| 2025-12 至 2026-05 | Mercor 连续发布 APEX、法律、软件工程、长程 agent 相关研究 | 说明产品覆盖从通用专家数据延伸到专业知识工作与 Agent 评测；不能由文章倒推新增团队人数 | B |
| 2026-02-27 | Scale 称接近一半的**新增数据训练项目**涉及 RL 环境（公司自述） | 提示其项目交付正在环境化，因此对环境平台、任务作者、验证器与数据取得人才有合理需求 | B |
| 2026-07-13 | Surge 的 `RL Environments Architect` 与 `Research Engineer, Coding Evaluation & Training Data` 两个仍开放岗位标注为当日发布 | 可直接确认：2026 年第三季度，Surge 同时寻求环境系统与 coding 任务/评测研发的正式人员 | A |
| 2026-07-24 | Mercor 的 `Research Engineer, Real Environments` 岗标注为当日发布 | 可直接确认：它在寻求把企业数据变成高保真 RL 环境、verifier 与训练/评测数据的全职工程师 | A |
| 2026-09-01 | Mercor 发布 1,928 个专家任务用于后训练的工程说明 | 说明其需要环境/harness/轨迹生命周期/专家任务制作能力；不是招聘人数 | B |
| 2026-09-15 | 四家公司当前职位快照 | 观察到环境、评测、专家运营、数据合作、FDE 与安全岗位并存 | C |

从这条时间线能成立的结论是“**能力类型正在变多、彼此耦合**”，而非“过去一年岗位总数增长了 X%”。Mercor 的研究发布时间见其研究目录。[^13] 若要做严格的同比，需要 LinkedIn Talent Insights、Revelio、Lightcast 等带历史归档的付费数据，或从这一日期开始按周保存 ATS 快照。

## 三、逐家公司：他们公开在招什么人

### 3.1 Scale AI：内部平台工程、专家供给和数据取得并行

**可见岗位与含义**

| 岗位/岗位群 | 人员性质 | 公开记录 | 实际工作内容 | 它说明的能力建设 |
|---|---|---|---|---|
| Staff Software Engineer, RL Environments | FTE，资深软件工程师 | 2026-09-15 仍开放；页面最后更新 2026-09-02 | 设计 sandboxed execution、环境打包/版本、rollout 编排、trajectory capture、verifier 框架和专家创作界面 | 不是“招标注员”，而是建设可规模化运行/验收 RL 世界的核心平台 |
| Data Acquisition Lead, Frontier Environments | FTE，商业/数据取得 | 2026-09-15 仍开放；页面最后更新 2026-08-21 | 找到持有下一类真实工作数据的企业，设计交易结构，连接商业、法务与研究 | 数据瓶颈不只是“找专家”，也包括取得企业操作数据的授权与交易 |
| Senior AI Product Manager, Finance Agents | FTE，垂直产品/领域人才 | 2026-09-15 仍开放；页面最后更新 2026-08-04 | 选择值得建模的金融任务，决定如何取得、结构化底层数据，并把领域知识产品化 | 除 coding 外，金融工作流被单列为 Agent/RL 数据产品方向 |
| ML Research Scientist（Evaluations / Agents / Agent Post-training 等） | FTE，研究人员 | 2026-09-15 板上仍可见多项 | 研究评测、agent 数据基础、post-training、鲁棒性与风险评测 | 环境生产还需要判断“训练是否真的泛化”、以及如何避免 reward hacking |
| Human Frontier Collective 的 SWE、ML、法律、医疗、金融 Fellows | 项目制专家供给，不应按 FTE 计 | 2026-09-15 快照中 16 个岗位 | 按不同专业国家/地区招募可参与项目的专家 | Scale 也在建外部专业供给漏斗，而不只扩内部工程团队 |

**这里的程序员究竟在做什么？**Scale 的 RL Environments 岗明确要求高吞吐编排、队列/调度、容器化执行、LLM agent/tool/MCP/evals 经验；它描述的是“数千环境、百万 rollout”所需的分布式系统问题。一个环境包含真实依赖、状态、工具和 grader；程序员要保证它能被重置、并发执行、记录轨迹，且验证器不会被模型通过投机取巧绕过。Data Acquisition Lead 与 Finance Agents PM 则补足了“取得数据—选择领域任务—产品化”的两端。[^5][^14][^15]

这与传统“写一个 benchmark”完全不同：它是一套生产平台。需要的是能写 Python、后端和系统软件、能用 Docker/VM/Kubernetes、理解 agent 工具接口的工程师；同时还需要金融、法律、医学等专家决定任务是否像真实工作。

**最重要的边界。**当前 228 个开放岗及 43 个关键词匹配，并不等于 43 个“AI 数据岗位”：其中混入企业部署、公共部门、Fellow、产品和研究岗位。它只能说明 Scale 已把 Agent/RL 相关工作拆成工程、研究、产品、数据取得和专家供给等多个部门，而非单一 coding 团队。[^1]

### 3.2 Surge AI：小型正式核心 + 高要求远程专家共同构造任务世界

| 岗位/岗位群 | 人员性质 | 可追溯时间 | 实际工作内容 | 对人才结构的解读 |
|---|---|---|---|---|
| RL Environments Architect | FTE，remote | `datePosted` 2026-07-13 | 设计模块化环境框架、API、课程/奖励/终止机制、遥测；做 coverage、trace audit、反 reward hacking QA | 典型的“环境架构师”：偏模拟/系统/质量工程，不是普通内容标注 |
| Research Engineer, Coding Evaluation & Training Data | FTE | `datePosted` 2026-07-13 | 为前沿实验室端到端负责 coding 数据项目、任务/RL 环境/evaluation，要求 3–6+ 年专业软件工程经验 | coding 在招聘中确实清晰可见；但这是一个岗位，不能据此排名所有数据投入 |
| Senior Software Engineer, Agentic Coding RL Environments | 合同/项目制资深工程师 | 2026-09-15 页面仍开放 | 将真实工程经验做成 coding 环境和 benchmark，编写任务、测试、rubric，review/red-team 输出 | 供应商把“做过生产系统的程序员”作为数据生产者招入，不只是让其给模型答案 |
| Human Data Architect、Data Ops、AI Ops | FTE/运营（具体合同以岗位为准） | 2026-09-15 当前职位页 | 设计专家任务、质量流程和交付运营 | 专家供给与 QC 仍是核心，不会被环境工程替代 |
| Lead Adversarial Engineer、Security Engineer、Forward Deployed Engineer/Researcher | FTE | 2026-09-15 当前职位页 | 对抗难例/安全、以及面向客户落地 | 加入安全与企业部署环节；不能简单称为 cyber 数据团队 |

Surge 在 2025-11 的公开研究把“多步骤工具使用、能在模拟工作世界中行动”明确为后训练/评测方向；2026 年 7 月出现上述两个正式岗位，二者在时间上相互印证。[^6][^7][^8] 但它们仍然无法回答：Surge 是否实际招满、每个岗位几人、coding 与其他领域的预算比例各是多少。

**从岗位组合看，Surge 不只是 coding。**其公开职位还包含 health-care/legal consultant、金融类项目分析、generative AI generalist、研究和现场部署等。coding 的特殊性在于它**往往**可以通过编译、单元/集成测试和静态检查获得较强的自动验收信号，资深工程师的供给也较容易通过项目制触达；这使它在职位标题和公开案例中格外显眼，而不是证明它压倒所有专业知识工作。SWE-bench 的 `FAIL_TO_PASS` 与 `PASS_TO_PASS` 测试就是公开的验收例子，但不应外推为 Surge 每个任务的具体机制。[^9][^18]

### 3.3 Mercor：把“人才市场”延伸为企业工作流采集、世界构建与交付

| 岗位/岗位群 | 人员性质 | 可追溯时间 | 实际工作内容 | 对人才结构的解读 |
|---|---|---|---|---|
| Research Engineer, Real Environments | FTE、现场 | `datePosted` 2026-07-24 | 与大型企业合作，将数据转化为高保真 RL 环境；构造 sandbox app、载入真实数据、从流程写 prompt、用企业专家/golden outputs 写 verifier | 最完整地串起“企业工作流 → 任务世界 → 训练/评测数据 → 客户交付” |
| Software Engineer, RL Studio | 远程小时制合同 | 2026-09-15 仍可见 | 构建 MCP server、连接真实软件与 sandbox、Docker/Linux、populate/snapshot hooks、权限与 runtime 验证 | 仍是程序员岗位，但采用可弹性采购的工程供给，而非只靠内部 FTE |
| Data/ML/Platform/Agentic Systems/Enterprise Evals/Frontier Data Products | 主要为 FTE（以单个岗位条款为准） | 2026-09-15 Careers 快照 | 数据平台、Agent 系统、企业评测、代码数据、产品化交付 | 形成研究、平台、环境与企业部署的完整内部链条 |
| Recruiting、Quality、Research Program、Fraud/Compliance | FTE/运营 | 2026-09-15 Careers 快照 | 专家招募、质量、项目运行、合规与风险防范 | 人才 marketplace 的真实难点还在筛选、反欺诈、质量和交付，而非仅撮合 |

Mercor 2026-09-01 的公开训练说明给出了底层技术连接：每个任务世界以容器镜像交付，运行时拉起 sandbox，harness 管理 rollout；专家任务、verifier、轨迹和训练器通过同一链路工作。[^10] 这让 `Research Engineer, Real Environments` 和 RL Studio 合同岗位的招聘内容不只是营销术语：它们确实对应一个可执行的任务生产系统。Mercor Careers 快照显示这些工程、运营与合规岗位在同一组织内并存。[^16][^17]

但仍须区分三件事：Mercor 的“数百万专家”、每天的专家支付额和公开职位，均是公司自述或市场网络指标；它们不等于正式 FTE、某类任务的真实产量，也不等于前沿实验室已采购的训练数据量。[^11]

### 3.4 Handshake：把职业网络拆成供给、交付、环境工程与企业 AI 四条线

| 岗位/岗位群 | 人员性质 | 2026-09-15 快照所见 | 对组织结构的含义 |
|---|---|---|---|
| Director Engineering, RLE Engineering；Software Engineer II, Reinforcement Learning Environments | FTE 工程 | 当前职位页列出，工程地点含印度 | 已出现专门的 RLE 工程组织与工程管理层，而不只是临时项目 |
| Engineering Manager, AI Evaluation Engineering；Senior Cloud Engineer, Agentic Infrastructure；ML Infrastructure / Operator Tooling | FTE 工程/平台 | 当前职位页列出 | 需要评测、云基础设施、操作者工具和机器学习基础设施共同支撑项目交付 |
| Strategic Projects Lead, Coding/RLE；Senior Product Manager, Coding；Senior Software Engineer, Coding | FTE 产品/工程/项目 | 近期快照中可见；不同抓取时职位数会变动 | coding 被明确设为一个产品/交付领域，但只是可见领域之一 |
| Data Partnership Strategist / Account Executive / Representative | FTE 商业与交付 | 当前职位页列出 | 在寻找可合作的数据拥有方、设计并推进数据合作 |
| AI Model Policy Trainer、AI Red Teamer、AI Safety Policy Evaluator、Strategic Projects Lead, Safety | FTE/项目条款须逐岗确认 | 当前职位页列出 | 安全评估和对抗测试也正在产品化、运营化 |
| AI Trainer/Fellow 项目 | 项目制独立承包商 | 职业页与帮助中心均明确 | 大规模弹性专家供给入口；不能计作内部工程 headcount |

Handshake 的职位板有一个特别值得注意的结构：`HAI Delivery Ops` 与工程、企业 AI、Employer Revenue 同时存在。它意味着公司正在做的不是单纯“把人派给模型公司”，而是至少包含（a）获取/管理专家，（b）项目交付和质量，(c) RL/eval 基础设施，(d) 数据合作与企业部署。[^2]

然而，当前职位页没有为每一职位公开可靠的首次发布日期，因而不能说这些岗位在过去 12 个月各招了多少人。我们只能说它们在研究日**仍然被寻求**。Handshake 的 75 万 community 与累计支付金额也只适合说明供给侧入口（且为公司口径）；其 trainer 项目不是固定全职工作。[^3][^12]

## 四、横向比较：招聘的共同生产链，而不是四家公司都在“招程序员”

| 生产环节 | Scale | Surge | Mercor | Handshake | 对数据市场的真正含义 |
|---|---|---|---|---|---|
| 取得真实工作数据 | Data Acquisition Lead | FDE / 垂直顾问 | 与企业合作的 Real Environments | Data Partnerships | 高价值数据要解决授权、脱敏、商业合同和领域选择 |
| 任务与世界设计 | Finance Agents PM、专家 Fellows | Human Data Architect、领域 consultant | Research Engineer, Real Environments | Strategic Projects、Coding/RLE | 数据单位从文本/标签变为完整工作任务和初始世界状态 |
| 环境/平台工程 | Staff SWE, RL Environments | RL Environments Architect | RL Studio、Agentic Systems | RLE Engineering、Agentic Infrastructure | **这里招的是程序员**：做沙盒、状态、工具、轨迹、并发和重置 |
| 验证/评测/安全 | Evaluations、Agent Robustness | Coding evaluation、adversarial/security | Enterprise Evals、verifier | Evaluation Eng、red team、policy | 将“看起来合理”换成可复现 reward、留出 eval 和风险测试 |
| 专家与交付运营 | Human Frontier Collective | Data/Ops、合同工程师 | Recruiting/Quality/Research Program | HAI Delivery Ops、Trainer | 把专业人员变成可持续、可审核、可结算的生产网络 |
| 客户部署 | Frontier Agents / FDE | FDE/Researcher | Enterprise delivery | Enterprise AI/FDE | 私有工作流必须在客户环境中适配，不能只卖一套通用数据 |

这张表的核心不是“这些公司把所有工作都软件化了”，而是：**环境工程的新增重要性并没有消灭专家、运营和数据合作；反而让这四类岗位相互依赖。**没有专家，任务失真；没有工程，任务无法反复运行；没有 verifier，rollout 没有可靠训练信号；没有数据合作和合规，企业工作无法进入环境。

## 五、这对“coding、cyber、专业知识工作谁在增加”意味着什么

### 5.1 可以由招聘得出的结论

* **环境/验证器/轨迹基础设施在增加。**四家都能观察到 RLE、Agent、评测、平台或同义岗位；其中 Surge 和 Mercor 有 2026 年 7 月的带发布日期正式岗位，Scale 和 Handshake 有研究日仍开放的明确岗位。这个方向的证据最强。
* **专业知识工作在进入产品化。**Scale 的 Finance Agents、Mercor 的 enterprise real environments、Handshake 的 data partnerships、Surge 的医疗/法律/金融顾问与企业研究，说明它们不只在买 coding 样本。
* **coding 依然是显眼且工程化程度高的一条线。**Scale、Surge、Handshake 都把 code/coding 写进明确职位；Surge 对此招有 3–6 年生产软件经验的研究工程师和合同资深工程师。原因是代码任务有可运行测试、失败日志与较低成本的自动验收，适合早期高频 rollout。
* **安全/对抗能力在增加，但不能等同于 cyber 数据。**Surge 的 Security/Adversarial、Handshake 的 Red Team/Policy/Safety 和 Mercor 的 fraud/compliance 是公开招聘信号。它们大多服务于模型安全、内容政策、环境/企业系统安全与质量控制；未见足够公开招聘证据可以把它们量化为“网络攻防训练数据大规模扩张”。

### 5.2 不能由招聘得出的结论

* 不能把 coding 相关职位更多、标题更容易检索，推成“LLM 当前主要在增强 coding”；
* 不能把一个 `RL Environments Architect` 职位，推成公司已拥有数千环境或耗费某个固定预算；
* 不能把合同专家/AI Trainer 的职位数，推成实际活跃专家、完成任务数或数据 token 数；
* 不能把职位标题中的 Finance、Legal、Healthcare、Security 排序成各领域训练数据采购金额；
* 不能根据某个职位一直挂着判断团队扩张，因为招聘冻结、难招、重复刊登和地域多岗位都会产生相同现象。

### 5.3 对此前判断的校正

如果问题是“与过去相比，真正增加的是什么”，最强的公开结论不是“coding 数据一定最多”，而是：

> **数据生产的增量重心正在从单轮标注/SFT，迁到能生成长程行动轨迹的 RL 环境、验证器、任务世界与企业工作流接入。**

coding 是其中最标准化、最容易自动验收、最常被公开展示的第一类环境；专业知识工作、computer use 与企业数据合作正在被纳入同一生产函数。公开招聘目前不足以给它们排出投入金额或总数据量的名次。

## 六、如何把这项研究变成可持续的领先指标

单次深挖只能给“能力地图”，不能给严谨的招聘增速。建议从本研究日开始维护一个每周/每月快照表，字段如下：

| 字段 | 记录方式 | 目的 |
|---|---|---|
| 职位 URL / ATS ID | 保留原始链接与快照日期 | 去重，避免同一职位反复计数 |
| 首次看到/关闭日期 | 以本地首次发现、最后可访问为准；不要冒充官方 posting date | 形成可比的开放时长 |
| 雇佣性质 | FTE / fixed-term / contractor / Fellow | 防止把弹性专家当 headcount |
| 生产环节 | 数据取得、任务、环境、verifier/eval、专家运营、FDE、安全 | 追踪真正的组织投入方向 |
| 领域 | coding、金融、法律、医疗、企业通用、computer use 等 | 观察领域变化，但不以职位数估算预算 |
| 技能词 | Docker、Kubernetes、MCP、sandbox、trajectory、verifier、rubric、red team 等 | 识别底层技术栈是否迁移 |
| 证据强度 | 官方带日期 / 官方快照 / 二手报道 | 使结论可审计、可撤回 |

连续 2–4 个季度后，才可以回答更强的问题，例如“环境工程岗占公开开放岗的比例是否上升”“专业领域由 coding 向金融/法律/医疗扩散是否持续”，且仍应写成**招聘需求的代理变量**，而非模型公司的训练预算。
