# Token 的价格：数据中心成本、效率与竞争

整理日期：2026-09-14  
数据截止日：2026-09-14（第 3 节软件效率、第 5.1 节 API 价格与第 6 节推理数据中心效率）  
状态：研究框架已整理；第 3 节软件效率与第 6 节硬件/系统平台比较已核验并附来源，其余具体性能、价格和训练成本数字仍须逐项附原始链接。

## 一句话结论

数据中心里的 GPU、电力、机架和接入资源可以同时变贵，而 Token 单价仍继续下降：决定性变量不是资源的绝对价格，而是每单位资源能够产出的、达到同等能力水平的 Token 数量。硬件、模型与服务系统的效率提升若快于资源价格上涨，单位 Token 成本就会下降；竞争决定这部分成本红利有多少会传导为 API 降价。

> 需要区分三件事：模型 API 的挂牌价、厂商自身的推理全成本、云上 GPU 租赁价格。三者相关，但不能互相替代。

## 1. 问题与分析框架

### 核心关系

在同一模型、同一服务质量和相同口径下，可用下式理解单位 Token 成本：

```text
单位 Token 成本 ≈ 单位时间的资源全成本 ÷ 单位时间产出的有效 Token 数
```

其中资源全成本包括硬件折旧、HBM/网络、机房、电力、冷却、运维和闲置冗余等；“有效 Token 产出”还受模型质量、延迟目标、上下文长度、并发量和缓存命中率影响。

因此，分析价格时应分开看四层：

| 层级 | 要回答的问题 | 主要指标 |
|---|---|---|
| 硬件与系统平台 | 同样资本与功耗能交付多少有效 Token？ | `Token/MW`、`$ / M Token`、延迟 SLA 下的有效吞吐 |
| 模型与算法 | 达到同等能力需要多少计算？ | 激活参数、精度、FLOPs/token、质量基准 |
| 服务系统 | 昂贵资源的利用率有多高？ | 批处理、KV Cache、缓存命中、TTFT、TPS、利用率 |
| 市场定价 | 成本下降会否传给客户？ | API 价、替代性、开源压力、毛利与补贴 |

## 2. 为什么 Token 单价会下降

### 2.1 硬件效率提升

新一代 GPU、专用推理芯片和机架级系统通常同时提高计算吞吐、HBM 带宽、内存容量及互联能力。即使新硬件的购置价、功耗或云租赁报价更高，只要每美元或每度电产出的有效 Token 增长更快，单位 Token 成本仍会下降。

### 2.2 模型、算法和精度优化

- **MoE（混合专家）**：总参数量可以很大，但一次推理只激活部分专家。
- **量化、剪枝和蒸馏**：以较低精度或更小模型接近原模型的效果。
- **推测解码、多 Token 预测**：一次验证或生成多个候选 Token，减少主模型 decode 工作量。
- **Attention 与 KV Cache 优化**：Flash Attention、分页/共享 KV Cache、前缀/提示缓存可减少重复计算或重复访存。
- **更好的训练与后训练方法**：同等任务能力所需的训练和推理计算可能下降。

对“固定能力水平”的比较，算法和模型架构的变化常与硬件进步同等重要，甚至更重要。

### 2.3 服务系统和规模效应

连续批处理、请求路由、解耦 prefill/decode、专家并行、低价地区部署和更高利用率，都会把固定成本摊到更多 Token 上。缓存命中尤其重要：相同的 API 用量表面上可能消耗大量输入 Token，但实际新增计算较少。

### 2.4 竞争与开源压力

开源或开放权重模型，以及多家闭源服务商的可替代供给，会压低 API 价格与毛利。没有竞争时，成本改善可主要体现为厂商利润；竞争激烈时，才更可能体现为用户看到的降价。

## 3. 软件如何提升 Token 产出效率

硬件决定带宽、算力与互联的上限；软件决定实际部署能吃到多少上限。软件升级可在不更换 GPU 的条件下改善吞吐、延迟或成本，但提升幅度并非固定：它取决于模型架构、精度、序列长度、并发、缓存命中率、服务 SLA 和质量评估。

### 3.1 量化：减少每 Token 的读写与计算

将权重、激活值或 KV Cache 从 FP16/BF16 降到 FP8、FP4、INT8/INT4 等较低精度，能降低模型占用和内存流量。以仅计算权重为例，70B 模型的 FP16 权重约 140 GB、FP8 约 70 GB、4-bit 约 35 GB；实际文件大小还会受量化元数据、分组和运行时缓冲影响。

在低 batch 的 decode 中，权重读取常是重要约束，量化因而可能显著提高吞吐；但质量、接受率、KV Cache、通信和内核效率也会影响最终结果。不能将“读取字节数减半”直接写成“实际 TPS 必然翻倍”。vLLM、TensorRT-LLM 与 SGLang 的当前文档均支持多种量化或低精度服务配置。

### 3.2 投机解码与多 Token 预测（MTP）

投机解码先由草稿模型或草稿头提出多个候选 Token，再由主模型批量验证；MTP 是其中的实现路径之一。它通过用额外计算换取更少的串行 decode 步骤，提高每次主模型前向传播的有效 Token 产出。

收益会受草稿接受率、模型架构和 batch 大小制约：对 dense 模型、低 batch、带宽受限的 decode 通常更有利；MoE 的多 Token 验证可能激活更多专家，高 batch 下额外验证计算也可能削弱收益。因此必须同时记录质量评估与服务条件。

一个可引用但高度特定的案例是：SemiAnalysis InferenceX 在 **DeepSeek-R1 FP4、8K/1K、150 tok/s/user、GB300 Dynamo TensorRT-LLM** 的图表中，将启用 MTP 前后的成本点列为约 $2.35 与 $0.11 / 百万 Token（约 21×）。这说明软件可在同一硬件上带来很大改善，但不应外推为 MTP 的通用倍数。[原始基准说明](https://inferencex.semianalysis.com/blog/inferencex-v2-nvidia-blackwell-vs-amd-vs-hopper)

### 3.3 推理引擎与服务框架

| 框架 | 文档确认的相关能力 | 使用时应避免的外推 |
|---|---|---|
| [vLLM](https://docs.vllm.ai/en/stable/) | PagedAttention、连续批处理、chunked prefill、prefix caching、量化、投机解码与分布式推理 | 不同模型和版本的实际吞吐差异很大，不能给出脱离 workload 的“数倍”结论。 |
| [TensorRT-LLM](https://github.com/NVIDIA/TensorRT-LLM) | 量化、KV Cache 配置、CUDA Graph、投机解码/MTP、解耦服务与并行配置 | 它是 NVIDIA GPU 优化栈；性能对模型导出方式、GPU、内核和配置敏感。 |
| [SGLang](https://github.com/sgl-project/sglang) | RadixAttention/prefix caching、连续批处理、paged attention、投机解码、prefill/decode 解耦与张量/流水/专家并行 | 功能存在不代表每项组合均成熟或在每个硬件后端可用。 |
| TGI 等其他服务框架 | 同样可参与吞吐、缓存与调度优化 | 本文不以功能表代替同口径 benchmark，不作框架性能排名。 |

这些框架共同解决的核心是：减少无效访存和 CPU 调度开销、提高 GPU 利用率、以及把不同请求和不同阶段安排到匹配的资源上。要比较框架，应固定模型、量化、序列长度、并发、TTFT/TPOT 或 tok/s/user 目标、硬件、软件版本和质量指标。

### 3.4 KV Cache、Attention 与批处理

- **连续批处理**：请求可动态进入或离开批次，降低传统静态批处理的空转；收益由到达率、延迟目标和请求长度决定。
- **PagedAttention / 分页 KV Cache**：以块管理 KV Cache，降低碎片、提高可服务并发；它改善的是内存利用和调度，不等于缓存命中。
- **Prefix / Prompt Cache**：相同前缀可复用已计算的 KV；命中时可显著降低 prefill 成本，但对没有共享前缀的请求没有同等效果。
- **KV Cache 量化、压缩与卸载**：通过容量、带宽、延迟之间的权衡，改善长上下文服务的单位成本。
- **FlashAttention、算子融合与 CUDA Graph**：减少 attention 的中间读写和启动开销；具体收益取决于形状、硬件与运行时。

### 3.5 并行、调度与解耦服务

大模型需要张量并行或流水并行；MoE 则可使用专家并行。Prefill 通常有更高计算强度，而 decode 常更依赖带宽和低延迟，因此可将二者拆到不同资源池（disaggregated serving），并通过 KV Cache 传输、缓存感知路由和动态调度协同。

这类系统级优化与 MTP、量化、机架级 NVLink 域会相互作用。前文的 GB300 65×/50×/35×是“硬件 + 全栈软件 + 特定工作负载”的结果，不能将全部增益归因于芯片，也不能把单一软件优化的局部结果相加。

### 3.6 训练侧的软件效率

训练同样受益于混合精度、激活检查点、ZeRO/状态分片、通信算子优化、编译与 kernel 优化、MoE 负载均衡等。它们通过提高 MFU、降低显存占用或减少通信等待来缩短训练时间；成本改善需要以训练质量、训练 Token、集群规模和有效利用率共同衡量。

## 4. 为什么数据中心资源涨价与 Token 降价不矛盾

AI 基础设施的总需求上升，会推高 GPU 租赁、供电接入、变压器、土地、冷却和网络等稀缺资源的价格；与此同时，硬件和软件效率提升又会降低每单位智能产出的成本。这是“总量紧张”与“单位效率改善”同时发生。

另一个关键区别是**单位价格与总账单**：Token 更便宜会诱发更长上下文、多轮 Agent、重试和批量自动化，因而总 Token 使用量和总数据中心支出仍可能上升。这是杰文斯悖论在 AI 服务中的表现。

## 5. 价格会降到哪里：分层而非单一地板

| 层级 | 价格趋势 | 长期约束 |
|---|---|---|
| 商品级、小模型、高批量任务 | 最容易快速降价，可能被免费层或补贴层覆盖 | 电力、折旧、服务运营与最低利润 |
| 中端“够用级”模型 | 随开源和标准化供给持续承压 | 全成本、延迟 SLA、模型质量差异 |
| 前沿旗舰与强推理模型 | 降价较慢，可能维持能力溢价 | test-time compute、稀缺能力、研发回收、容量约束 |

原始笔记中的区间判断是：商品级未来可能逼近电费与极低折旧，中端趋向合理全成本，前沿强推理仍保有明显溢价。具体的美元/百万 Token 数字必须按输入/输出、是否缓存、地区、承诺量、批量和服务等级分别核验。

### 5.1 正确的 API 价格曲线：固定模型 ID，而不是新旧模型替代

如果问题是“**Claude Sonnet 4 在最近半年有没有降价**”，观察对象必须固定为 `anthropic/claude-sonnet-4`。此前用 Sonnet 4.5 → 4.6 或其他新旧型号拼接的方式，只能说明厂商的产品策略，**不能回答同一模型的价格变化**，不再作为本文的价格曲线。那类市场事件原始链接仍留在 `factcheck/data/token_api_price_events_12m.csv`，仅供背景查询。

OpenRouter 的每个模型页提供 `Price History`，可选择 **Listed**（供应商挂牌价）或 **Effective**（按实际流量、缓存命中与供应商路由后的成交均价），并按供应商显示输入和输出价格，时间范围可选 1 周、1 个月、3 个月、1 年和全历史。Sonnet 4 的页面在此：[OpenRouter：Claude Sonnet 4](https://openrouter.ai/anthropic/claude-sonnet-4)。

对本文的研究用途，口径固定如下：

| 研究问题 | 应选的 OpenRouter 数据 | 不应选的数据 | 原因 |
|---|---|---|---|
| 同一模型是否调价 | **Listed**，同一模型 ID、同一供应商、输入/输出分别看 | 跨版本的 Sonnet 4 → 4.6 | 只有前者是同一服务的挂牌价序列 |
| 实际客户平均账单是否下降 | **Effective**，并保留各供应商 token share 和 cache hit rate | 将 Effective 当成厂商调价 | Effective 会随缓存命中和路由结构变动，即使挂牌价不变也会下降 |
| 模型替代后的性价比 | 新旧模型分别的 Listed 价格 + 独立能力测评 | 把新模型价格直接接到旧模型曲线 | 这研究的是“同等任务成本”，不是“同模型调价” |

已核验的固定模型例子是 `anthropic/claude-sonnet-4`：一个每 12 小时从 OpenRouter API 快照、并回溯了约 20 个月 git 历史的第三方记录，在 2025-05-23 至 2026-09-13 间仅保留一个价格点：**输入 $3/M、输出 $15/M**，即其 OpenRouter 聚合 `Listed` 价没有变化。这个结论也与 Anthropic 在 2025-05-22 发布 Sonnet 4 时的 $3 / $15 首发价相符。[OpenRouter 历史快照数据](https://github.com/jvrck/openrouterlist/blob/main/data/history/prices.json) / [Anthropic 发布页](https://www.anthropic.com/news/claude-4)

| Sonnet 4 指标 | 2025-05-23 | 2026-09-13 | 期间变化 | 能否解释为模型降价 |
|---|---:|---:|---:|---|
| OpenRouter 聚合 `Listed` 输入 | $3/M | $3/M | **0%** | 可以：同一模型的基础挂牌价未变 |
| OpenRouter 聚合 `Listed` 输出 | $15/M | $15/M | **0%** | 可以：同一模型的基础挂牌价未变 |
| OpenRouter `Effective` 输入 | 随时间变动 | 随缓存/路由变动 | 不能用首末值概括 | 不可以：它不是基础标价 |

所以，页面中出现的“中间上涨”不是 Sonnet 4 基础挂牌价上涨。`Effective` 输入价会把缓存读取、缓存写入和供应商路由混在一起计费：当前页面显示 Bedrock 路由 `Listed` 输入仍为 $3/M、cache hit rate 约 37.5%、`Effective` 输入约 $2.025/M；Google Vertex Global 的对应值约为 54% 和 $1.636/M。命中率下降、流量从高缓存路由迁往低缓存路由，或区域性 provider（可有不同价表）占比上升，都会让图线向上，即使模型的 $3/M 基础价完全未变。[OpenRouter 模型页](https://openrouter.ai/anthropic/claude-sonnet-4)

OpenRouter 没有发现文档化的官方历史下载 API；上表使用的历史点来自独立的 OpenRouter API 快照项目，故应标为“第三方快照”，而非 Anthropic 官方逐日价表。但对这个问题，它给出的结论是明确的：**Sonnet 4 的公开基础 Token 标价没有随硬件升级而下降。**

**这组数据真正支持的判断：** API Token 价的下降不是随硬件效率平滑发生，而是呈现“两极”——成熟闭源模型可长期不变；新入场的低价型号可以在数月内降 65%–80%；开放模型的路由价甚至会先涨后跌、数日翻倍。对“Token 价格还有多少下降空间”的估算，硬件 `Token/$` 只能给成本地板的方向；API 价的速度与幅度取决于该档位是否面临替代品和产能竞争。

### 5.3 最近半年真实价格变化：固定 3 月 Top‑30、固定权重、固定日历

**直接答案：不是每周 −10% 或 −15%。** 对同一批在 2026-03-14 已经存在的高用量模型，六个月后仍可购买的相同型号，OpenRouter 广告输入价累计 **−0.5%**、输出价累计 **+0.2%**。把这 183 天机械折成复合周率，分别只是 **−0.020% / +0.009% 每周**；这不是“每周固定调价”的断言，而是对全期净变化的单位换算。此前的“Top-30 上市至今”把不同模型、不同上市日混在一起，**不能回答这个问题，现已撤出主结论。**

这里采用唯一可直接回答时间问题的口径：先以 2026-02-13 至 03-14 的 30 个完整 UTC 日 OpenRouter Token 用量，选出当时的 Top-30；这 30 个模型的 **3 月 Token 用量永久固定为权重**。之后每月只观察这批完全相同的模型，既不把后来上市的模型补进来，也不因当前用量高而改权重。免费/隐身模型没有正价格，9 月已经下线的型号也没有 9 月可购买的报价，均不把其最后一个旧价硬带到 9 月。因而最终是 **21 个持续可购且全期有正价格的模型，覆盖初始 Top-30 的 42.068T Token、80.0%**；剩余 20.0% 被明确报告为覆盖缺口，而不是补零或用替代模型伪造趋势。

价格是每个端点当日或此前最近一条 OpenRouter 模型级广告输入/输出价（$/M），再按固定 3 月 Token 权重计算：

```text
固定篮子的平均 $/M = Σ(3 月模型 Token 权重 × 该模型当日 $/M) ÷ Σ(3 月模型 Token 权重)
价格指数 = 当月固定篮子平均 $/M ÷ 2026-03-14 固定篮子平均 $/M
```

| 端点 | 输入平均 $/M / 指数 | 输入环比 | 输出平均 $/M / 指数 | 输出环比 |
|---|---:|---:|---:|---:|
| 2026-03-14 | $1.072 / 100.0 | 基期 | $5.371 / 100.0 | 基期 |
| 2026-04-13 | $1.034 / 96.5 | **−3.5%** | $5.338 / 99.4 | **−0.6%** |
| 2026-05-13 | $1.035 / 96.6 | +0.1% | $5.365 / 99.9 | +0.5% |
| 2026-06-13 | $1.031 / 96.2 | −0.4% | $5.318 / 99.0 | −0.9% |
| 2026-07-13 | $1.030 / 96.1 | −0.1% | $5.320 / 99.0 | +0.0% |
| 2026-08-13 | $1.086 / 101.3 | **+5.5%** | $5.430 / 101.1 | **+2.1%** |
| 2026-09-13 | $1.066 / 99.5 | **−1.8%** | $5.383 / 100.2 | **−0.9%** |

所以半年内的真实描述是：**4 月输入价有一次约 3.5% 下调；8 月反而上涨；9 月回落；净结果接近 0。** 不能用一个虚构的“每周降价斜率”概括成持续下降。尤其不能把新模型首发后从高价降到低价，混入成熟模型的同一时期价格变化。

这也执行了你指定的 Luna 处理：2026-07-31 至 08-17 的临时低价不进入长期结论；更关键的是 Luna 在 7 月才上市，根本不在 3 月固定篮子内，因而不会污染这条半年曲线。该指数仍是 OpenRouter 的模型级广告/路由价，不是各厂商直接 API 合约价。其他无法从公开记录判明的短期优惠不能被我主观“修正”为标准价；它们会留在月度实测中，且是这条曲线的已披露局限，而不被年化或外推成市场趋势。

原始排名数据固定在 [2026-09-14 的镜像 commit](https://github.com/IAPS-AI/OpenRouter-OS-Rankings/commit/9ca669e36c5c3c908402e013b53c4449622e0cfe)，它镜像 [OpenRouter 官方 `rankings-daily` 数据集](https://openrouter.ai/docs/api/api-reference/datasets/get-rankings-daily)；价格历史固定在 [2026-09-14 的价格 commit](https://github.com/jvrck/openrouterlist/commit/6ffc63058b581c2e4f4bed1f2c68afa163fb29e6)。完整 30 行、每个月的首末价、下线标记和覆盖缺口在 `factcheck/data/openrouter_fixed_march30_monthly_price_index_2026-09-13.csv`；复算脚本为 `factcheck/verify_openrouter_fixed_march30_price_index.py`。

**Luna 的两个百分比并不冲突，但此前把它们都简称为“价格变化”是错误写法。** 同一第三方 OpenRouter 价格快照的完整序列是：2026-07-10 为 **$1/$6**，07-28 为 $0.50/$3，07-31 为 **$0.10/$0.60**，08-18 起为 **$0.20/$1.20**。故从首次可见价到 09-13 是 **−80%**；而从 08-15 的异常低点到 09-13 则是 **+100%**。OpenAI 同期公开标准 API 价为 $0.20/$1.20，快照没有记录 $0.10/$0.60 对应的 provider、服务层级或优惠条款。

本文的**长期标准价曲线删除 07-31 至 08-17 这段临时低价**：Luna 只按 `$1/$6 → $0.20/$1.20` 处理，即上市后标准价 **−80%**；不把 `$0.10/$0.60 → $0.20/$1.20` 计为长期涨价，也不把 `$0.10/$0.60` 计为长期价格地板。它因此**不改变**“上市至今”Top-30 标准价加权降幅（输入 −35.6%、输出 −36.9%），但会消除原始最近 29 天面板中 Luna 造成的 +100% 假象。这里的“标准价”是为长期研究构造的清洗口径，而非宣称已知该临时低价的具体优惠机制。[OpenAI Luna 定价页](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

此前前 10 的“约每周 −8%”是把每个型号从各自首发日到截止日的几何周变化再加权；它可以描述那一批新品的**生命周期降价速度**，却不是固定日历时间的市场价格曲线，不能再用来回答“最近每周价格下降多少”。本节以后以匹配时间面板回答时间问题，以“上市至今”指数回答新品价格战问题。

这两组旧审计支持的仅是：**高用量新型号的上市后挂牌价可下调约 36%–37%，而一个短样本 29 天路由价面板可显示约每周 −4%。** 前者不是同一日历期，后者不是固定 3 月篮子；两者都不能覆盖或推翻上文的半年主指数。硬件 `Token/$` 的改善因此只能说明成本地板下降的潜力，不能机械地当作 API Token 标价的周降幅。

**对本文核心问题的用法：** 用第 6 节估计“成本地板还有多少下行空间”，用固定模型 ID 的 `Listed` 曲线观察“厂商将多少成本红利传给用户”。前者是工程效率，后者是竞争与产品定价；两者需要并列追踪，不能相乘。

### 5.5 Top-10 模型：Token 增长不等于对应挂牌消费额增长

OpenRouter 的 Top-10 模型 30 日 Token 从 2026-04-10 的 **50.218T** 升至 2026-10-08 的 **393.927T（7.84×）**。但公开排名只给 `total_tokens`，不披露输入/输出拆分、缓存、折扣、BYOK 或分成，因此不能称为平台或模型厂商“营收”。按历史模型广告价和一个透明的 **75% 输入 / 25% 输出**情景复算，价格可覆盖部分的**挂牌推理消费额**为约 **$99.2M → $124.5M**，并没有随 Token 同倍增长；低价/免费模型替代是主要原因。这是价格混合效应的证据，不是市场实际收入只增长 25% 的结论。

其中 2026-07-10 的 **$255.1M** 是该情景的最高点，但不能读成实际营收峰值：三款 Claude 以 **20.3%** 的 Top-10 Token 对应 **86.7%（$221.2M）** 的情景额；至 8 月，这三款均不在 Top-10，尽管总 Token 继续增长 31.9%，情景额却降至 $47.1M。原因是模型组合从高价 Claude 转向低价/免费模型，而不是可确认的全市场需求或结算收入坍塌。

## 6. 推理效率：应如何比较硬件

### 6.1 核验结论

本节研究的对象是数据中心：**平台升级后，每 MW、每美元全成本能多产出多少 Token；这会把模型的 Token 价格地板压低多少？** 因而结论只采用 `tok/s/MW`、`Token/$` 与 `$ / M Token`；芯片规格和单卡吞吐最多只能解释机制，不能作为价格推断的证据。

对 API Token 定价，**推理**是直接变量；训练成本通过摊销间接影响价格。一个已大规模使用的模型，新增 Token 的价格地板主要由推理的硬件折旧、功率、机房和运维成本决定，而不是一次性的预训练成本。

```text
推理全成本 / M Token ≈ 数据中心全成本 / 小时 ÷（有效 Token / 小时）× 1,000,000
Token API 价格 ≈ 推理全成本 + 研发/训练摊销 + 产品/销售成本 + 利润
```

### 硬件平台总表：从 H100 到 Vera Rubin

这是本文硬件部分唯一用于判断 Token 成本的主表。`✅` 是同模型、同序列长度、同交互性目标下的公开推理实测；`🟡` 是由机柜规格和“Rubin 约为 GB300 两倍采购价”推导的情景；`—` 意味着没有合格的 `Token/$` 或 `Token/MW` 数据，不能为了凑成连续曲线而填数。

| **H200 → B200** | ✅ **2.15×**（$0.213 → $0.099/M） | ✅ **2.44×**（1.161M → 2.837M tok/s/MW） | 同模型、8K/1K、50 tok/s/user。 |
| **B200 → GB200 NVL72** | ✅ **0.85–3.87×** Token/$ | **—** | DeepSeek-R1 FP4 1K/1K、Dynamo TRT-LLM + MTP、解耦服务；25–60 tok/s/user 约 1×，75–200 为 1.15–3.87×，225–250 时 B200 又可更便宜。 |
| **GB200 NVL72 → GB300 NVL72** | ✅ **0.85–1.03×** Token/$（成本 **+18% 至 −3%**） | ✅ **0.93–1.14×** | DeepSeek-R1 FP4 8K/1K 三个 SLA 点；GB300 有效吞吐 +5%–29%，但每单位 TCO 更高。 |
| **GB300 NVL72 → Vera Rubin NVL72** | 🟡 **1.37–1.67×**（成本约 **−27% 至 −40%**） | 🟡 **1.72–2.08×** | 规格 + 同资本情景：约 2 个 GB300（$4.0M × 2）对 1 个 Rubin（约 $7.8M）；分别对应 HBM 带宽受限与 dense 计算受限。 |

**不能把前四行相乘。** 原因是 H100→H200、H200→B200 的 SLA 分别为 45 和 50 tok/s/user；B200→GB200 是 FP4 1K/1K、GB200→GB300 是 FP4 8K/1K；Rubin 还是规格和采购价情景，不是同一基准的实测。相乘会制造一条看似精确、实际没有共同实验基础的“H100→Rubin 成本曲线”。

但有两条跨代直接实测可作为现实锚点：H100→B200 为 **4.77× Token/$、5.65× Token/MW**（45 tok/s/user），H100→GB200 NVL72 为 **7.16× Token/$、8.35× Token/MW**（54 tok/s/user）。这说明从 Hopper 存量平台升级到 Blackwell 机架平台，推理成本确有约 79%–86% 的下降空间；但它们同样不能和 Rubin 的规格推算机械相乘。

对 Rubin 这一行，最重要的同资本算术是：

```text
dense 算力：3,600 ÷ (2 × 1,080) = 1.67×
HBM 带宽：1,580 ÷ (2 × 576) = 1.37×
功率：227 ÷ (2 × 142) = 0.80×
```

所以在模型确实受 dense 计算限制时，同资本 Rubin 的 `$ / M Token` 规格先验约低 40%；在 HBM 带宽限制的 decode 中约低 27%。相反，Rubin 的 HBM 容量只有同资本两柜 GB300 的一半；若 KV Cache 或超长上下文并发容量是瓶颈，这个优势会缩小。完整复算和采购价边界见 6.4。

为什么 B200→GB200 会从接近 1×到 3.87×：两边的 GPU 世代接近，差异是 GB200 把 72 个 GPU 放在一个 NVLink 域内。DeepSeek-R1 每个 Token 约有 120 次 MoE all-to-all；当 75–200 tok/s/user 需要宽专家并行时，B200 的通信要跨 8-GPU NVLink 岛并走 RoCE，GB200 则仍留在 NVLink，因此成本优势最高到 3.87×。在 25–60 的高并发点，两边都能把通信隐藏在计算后面，优势只有 1%–6%；到 225–250，运行时并行配置和瓶颈再次改变，B200 的 `$ / M Token` 反而低约 4%–15%。因此它不是“一个固定的 GB200 倍数”，而是一条随 SLA 变化的 MoE 通信曲线。[B200 vs GB200 原始测试](https://inferencex.semianalysis.com/blog/gb200-nvl72-vs-b200-disagg-deepseek-r1-fp4-dynamo-trt)

GB200→GB300 没有稳定成本改善也有精确原因：该基准的 TCO 假设为 GB200 **$1.86/GPU·h**、GB300 **$2.31/GPU·h**，即 GB300 高约 **24%**。在 93、162、231 tok/s/user 三个点，GB300 的有效吞吐仅分别高 **9%、29%、5%**；只有 +29% 超过 TCO 溢价，故 `$ / M Token` 仅低约 3%，其余两点分别高约 13% 和 18%。对应的 `Token/MW` 也是 **−4%、+14%、−7%**，而不是单向上升。根本原因是 GB300 相对 GB200 增加的是 dense 计算和 HBM 容量，HBM 带宽与 NVLink 带宽没有增加；该类 MoE 推理在部分 SLA 下受带宽/通信而非 dense 算力限制。[GB200 vs GB300 原始对照](https://inferencex.semianalysis.com/compare/deepseek-r1-gb200-vs-gb300)

来源：[H100 vs H200](https://inferencex.semianalysis.com/compare/deepseek-r1-h100-vs-h200)、[H200 vs B200](https://inferencex.semianalysis.com/compare/deepseek-r1-b200-vs-h200)、[H100 vs B200](https://inferencex.semianalysis.com/compare/deepseek-r1-b200-vs-h100)、[H100 vs GB200](https://inferencex.semianalysis.com/compare/deepseek-r1-gb200-vs-h100)、[GB200 vs GB300](https://inferencex.semianalysis.com/compare/deepseek-r1-gb200-vs-gb300)。

硬件与软件仍必须分表：上表是更换数据中心平台后的单位经济性；下表是**硬件不变**时通过 MTP、量化等得到的增益。两类增益可能已经同时存在于某些实测平台配置中，直接相乘会双重计算。

### 软件提升

| 软件变量 | 固定不变的内容 | 实测 Token 吞吐变化 | 应如何理解 |
|---|---|---:|---|
| **H200：MTP 关闭 → 开启** | DeepSeek-R1、H200、FP8、8K/1K | **1.27–1.93×** | 单项投机解码优化在 Hopper 上的实测量级约 1.3–2×。 |
| **B200：MTP 关闭 → 开启** | DeepSeek-R1、B200、FP8、8K/1K | **2.44–2.80×** | 同一项优化在 Blackwell 上可达到约 2.5–3×；软件收益会被硬件能力放大。 |

软件部分可直接概括为：**单项成熟推理优化通常是约 1.3–3×；低精度部署在质量允许时通常再给约 2–4×。**

### 训练：效率会提高，但不是 Token API 降价的主传导项

训练也应看 `训练 Token / $` 与 `训练 Token / MW`，但公开、跨代、同模型、同 GPU 数、同软件版本的训练数据远少于推理数据，不能伪造出一条精确的训练成本曲线。已找到的相近公开点是 Llama 2 70B LoRA：8 张 H200 完成 MLPerf 目标用时 21.84 分钟，8 张 GB200 用时 10.34 分钟，约 **2.11×** 的系统训练加速；不过该结果在 NVIDIA 页面被明确标为 **unverified**，只能作为数量级参考，不能用于成本模型定值。

对 Token API 的定价含义是：训练效率改善会降低新模型的开发/训练摊销并加快模型迭代，但成熟 API 的边际 Token 成本主要仍由推理决定。分析价格下降空间时，应以本节的 `$ / M Token` 与 `tok/s/MW` 推理数据为主，训练效率作为利润率和新品定价的二级变量。[MLPerf 训练结果说明](https://developer.nvidia.com/blog/nvidia-blackwell-delivers-up-to-2-6x-higher-performance-in-mlperf-training-v5-0/)

数据来源与边界：

- 数据中心单位经济性表中的平台点位来自 SemiAnalysis InferenceX 的 [H100 vs H200](https://inferencex.semianalysis.com/compare/deepseek-r1-h100-vs-h200)、[B200 vs H100](https://inferencex.semianalysis.com/compare/deepseek-r1-b200-vs-h100)、[GB200 vs H100](https://inferencex.semianalysis.com/compare/deepseek-r1-gb200-vs-h100) 与 [GB300 vs H200](https://inferencex.semianalysis.com/compare/deepseek-r1-gb300-vs-h200) 页面。
- H200/B200 的 MTP 数据来自对应的 [H200 对比](https://inferencex.semianalysis.com/compare-spec-decode/deepseek-r1-h200-fp8-mtp-vs-none) 和 [B200 对比](https://inferencex.semianalysis.com/compare-spec-decode/deepseek-r1-b200-fp8-mtp-vs-none)。该基准提示不同引擎的 MTP 接受率实现可不同，因此这里应读作“启用 MTP 的生产优化包效果”，不要把小数点后的差额归因给 MTP 算法本身。

### 6.2 GB300 的 65×/50×/35×到底是什么

该组数字有明确出处，不能删掉；但必须附上完整限定：

- 来源为 [NVIDIA 推理性能页](https://developer.nvidia.com/deep-learning-performance-training-inference/ai-inference)，其标注数据来自 SemiAnalysis InferenceX，时间为 Q1 / 2026-04；
- 比较对象是 **HGX H200 数据中心配置** 与 **GB300 NVL72 数据中心配置**；
- $0.123/M Token 的 GB300 点位对应 **116 TPS/user**、Dynamo 与 TensorRT-LLM；
- 因此 65×、50×和 35×是同一套全栈配置、特定低延迟 Agent 工作负载与 TCO 假设下的相对结果，包含硬件、FP4/量化、NVLink 规模、并行策略和服务软件的共同作用；
- SemiAnalysis 的公开对比页也明确提示：解耦 prefill/decode 的配置可能按不同阶段的资源计量，不能与聚合配置直接作 apples-to-apples 对比。[示例页面](https://inferencex.semianalysis.com/compare/minimax-m27-gb300-vs-h200)显示，在另一模型和 8K/1K 序列条件下，GB300 配置对 H200 配置的 Token 成本优势会显著小于该 65×/35×宣传点。

### 6.3 Vera Rubin：两个版本的说法不能混用

NVIDIA 的两位数主张不进入 6.1 主表，原因是它们不是可泛化的同条件实测：Kimi-K2-Thinking、32K/8K 下称 Rubin 对 GB200 最多 10× Token/MW、成本降至 1/10，但页面标注“subject to change”；DeepSeek V4 Pro 的 AgentX 下称 Rubin 对 GB300 最多 30× Token/MW、35× 更低成本，但为 NVIDIA 早期自测、仍待 SemiAnalysis 审核；配合 Groq 3 LPX 的 35×还包含 LPU 系统，不是 Rubin NVL72 的独立效果。[Vera Rubin 产品页](https://www.nvidia.com/en-us/data-center/vera-rubin-nvl72/)；[NVIDIA AgentX 说明](https://blogs.nvidia.com/blog/vera-rubin-nvl72-efficiency-ai-agents/)。

### 6.4 Vera Rubin NVL72：由机柜规格推导的 Token/MW 先验

在没有独立、同模型、同 SLA 的 Rubin 实测前，只能做**规格推导**，不能把它写成已验证的 `$ / M Token` 结论。以下以 GB300 NVL72 为基准，采用机柜对比中约 142kW（GB300）和约 227kW（Rubin）的功率假设；Rubin 规格仍为 NVIDIA 标注的 preliminary。

按一对一机柜规格，Rubin / GB300 的 dense 计算、HBM 带宽、NVLink/scale-out 总带宽、功率比分别约为 **3.33×、2.74×、2.00×、1.60×**。故三种单一瓶颈的 `Token/MW` 先验分别为 `3.33 ÷ 1.60 = 2.08×`、`2.74 ÷ 1.60 = 1.72×`、`2.00 ÷ 1.60 = 1.25×`。实际端到端请求同时包含 prefill、decode、KV Cache 和通信，因此面向常规大模型推理的审慎规格先验是 **1.3–2.1× `Token/MW`**；不能把三项相乘。

`$ / M Token` 不能只由规格推出。若 Rubin 与 GB300 的每小时全平台 TCO 比为 `k`、某个工作负载的每柜有效 Token 吞吐比为 `r`，则：

```text
Rubin 的 $ / M Token ÷ GB300 的 $ / M Token = k ÷ r
Rubin 的 Token/$ 改善 = r ÷ k
```

公开的二手转述中，Morgan Stanley 对 hyperscaler 的一组估算为 VR200 NVL72 约 **$7.8M**、GB300 NVL72 约 **$4.0M**，即采购价约 **1.95×**；但其他媒体援引的不同配置报价是 GB300 约 $6–6.5M、Rubin 最高约 $8.8M。因此“两倍”可作为成本模型情景，**不是 NVIDIA 的公开定价，也不是已确认的 TCO**。[Morgan Stanley 估算的媒体转述](https://www.tomshardware.com/tech-industry/artificial-intelligence/nvidias-memory-costs-soar-485-percent-latest-ai-systems-now-cost-usd7-8-million-to-build-memory-now-comprises-25-percent-of-the-total-cost-rubin-gpus-a-mere-usd50-000-apiece)

在“同样采购资本”这个问题下，正确的比较单位是 **约 2 个 GB300 NVL72 对 1 个 Rubin NVL72**，而非一对一机柜。按 $4.0M × 2 ≈ $7.8M 复算：

| 同资本包的资源 | 约 2 × GB300 NVL72 | 1 × Rubin NVL72 | Rubin / GB300 包 |
|---|---:|---:|---:|
| dense NVFP4 峰值算力 | 2,160 PFLOPS | 3,600 PFLOPS | **1.67×** |
| HBM 总带宽 | 1,152 TB/s | 1,580 TB/s | **1.37×** |
| HBM 总容量 | 41.4 TB | 20.7 TB | **0.50×** |
| 柜内 NVLink 总带宽 | 260 TB/s（分属两个 72-GPU 域） | 260 TB/s（一个 72-GPU 域） | **1.00×** |
| scale-out 总带宽 | 115.2 Tb/s | 115.2 Tb/s | **1.00×** |
| IT 功率（机柜假设） | 284 kW | 227 kW | **0.80×** |

这组数据给出三个可以直接写入模型的结论：

1. 若推理确为 **dense 计算受限**，且能将算力比例转化为有效吞吐，同资本下 Rubin 的 `Token/$` 规格先验为约 **1.67×**，对应 `$ / M Token` 约低 **40%**；
2. 若推理确为 **HBM 带宽受限的 decode**，且能将带宽比例转化为有效吞吐，同资本下为约 **1.37×**，对应 `$ / M Token` 约低 **27%**；
3. 若主要受 **总互联带宽**约束，规格没有给出总量提升；Rubin 的价值可能来自同一 72-GPU 域内带宽加倍和更低延迟，但不能仅凭规格断言 Token 成本下降多少。

此外，1 个 Rubin 机柜的功率约比 2 个 GB300 机柜低 **20%**，所以电费、冷却和供电容量这一部分成本对 Rubin 有利；其精确影响仍取决于 PUE、电价和各项 TCO 的权重。相反，Rubin 的 HBM 总容量只有同资本两柜 GB300 的一半；若业务受 KV Cache 容量或超长上下文并发限制，必须增配 Rubin 容量，以上 Token/$ 优势会被削弱甚至消失。

此前按“一柜 Rubin 对一柜 GB300”写的 TCO 比虽然可以描述单柜成本，但不是“相同资本支出”的正确分母；对本问题不应据此得出 Rubin 可能在计算或 HBM 带宽工作负载上效率下降的结论。真正的端到端 `Token/$` 仍需同模型、同 SLA 实测确认，但规格与已知采购价假设支持的方向是：**计算型推理约 +67%，带宽型 decode 约 +37%，而不是下降。**

这与 NVIDIA 的 AgentX “最高 30× Token/MW、35× 更低 $/M Token”并不冲突，但也不能相互替代：30×是 NVIDIA 在 DeepSeek V4 Pro、160 tok/s/user 的特定长上下文 Agent 轨迹上，以全栈软件和功率调度得到的早期测量，且明确 **pending SemiAnalysis review**；上表是仅由公开机柜规格得到的、面向一般推理的保守工程先验。[NVIDIA AgentX 口径说明](https://developer.nvidia.com/blog/nvidia-vera-rubin-and-blackwell-set-a-new-standard-for-agentic-ai-performance-per-watt/)

### 6.5 Decode、Prefill 与 HBM：只作机制解释

低 batch、大模型的 **decode** 常受权重读取和 HBM 带宽强烈影响，但不应写成“几乎完全由 HBM 决定”。实际性能还取决于 KV Cache、量化、并行通信、批处理、软件内核与延迟 SLA；随着 batch 上升，瓶颈也会变化。

HBM、KV Cache、量化与通信会共同决定系统的瓶颈；它们只用来解释为什么某个数据中心配置的 `Token/MW` 或 `$ / M Token` 改变，不能从理论带宽或单设备显存直接推导出数据中心的 Token 成本。

## 7. 训练与推理：成本结构不同

| 场景 | 主要瓶颈 | 关键变量 | 硬件/系统重点 |
|---|---|---|---|
| 训练 | 计算与通信 | 训练 Token、FLOPs、MFU、并行策略 | 算力、互联、网络、高利用率 |
| 推理 prefill | 计算与内存的混合 | 输入长度、batch、KV Cache | FLOPS、带宽、调度 |
| 推理 decode | 常常偏向内存带宽 | 权重大小、精度、并发、输出长度 | HBM 带宽/容量、KV Cache、低延迟服务 |

密集模型的常用训练计算近似为：

```text
训练 FLOPs ≈ 6 × 参数量 × 训练 Token 数
```

这不是 MoE 的通用公式。MoE 应至少说明激活参数、路由、通信以及计算口径；GPU-hours 和训练成本还会随有效利用率、集群故障、云价/自建成本和训练轮次而变化。

## 8. 后续观察指标

- 主要模型 API 的输入、输出、缓存读写和 batch API 定价变化；
- 达到同一能力水平所需模型规模、推理 Token 与推理时间的变化；
- 新硬件在真实服务 SLA 下的 tokens/$、tokens/W，而非只看峰值 FLOPS；
- 开源模型与闭源模型在目标工作流上的能力差距；
- 电力接入、机架交付、变压器、冷却和 HBM 的供给是否成为更强约束；
- Agent 使用量增长是否快于单位成本下降，从而推高总支出。

## 小结

Token 是算力、模型效率和服务系统共同产出的产品。未来更可能出现“商品级 Token 趋近边际成本、前沿能力保持溢价”的分层格局；总数据中心支出与 Token 单价可以沿相反方向变化。判断这一趋势时，最重要的是固定能力与服务口径，并区分硬件、软件、系统和市场定价四个层面的贡献。
