# 研究 SOP 后续模块推进规划

日期 2026-11-18。首项已获确认并完成本地验证，实战试点待下一次适用研究任务。本文件记录营收和估值 Skill 落地后的推进顺序。此前的模块化方案保留为历史背景，本轮以已经运行的流程和实际漏项为依据。

## 1. 背景与目标

CoreWeave 和 Nebius 首版 HTML 把主报告迁移缩成了 Q3 局部更新，遗漏三完整财年。两份报告随后补齐，营收 Skill 也加入了独立的期间覆盖脚本。这个案例说明，模块化要改善两个结果：开工确定的范围能延续到交付，报告中的实际缺项能被指出并定位。

后续每次只推进一个模块。该模块应有明确触发场景、实际输出和可验证的通过条件。用旧报告中的已知漏项做回归，通过后才选下一项。

## 2. 范围与非目标

- 本规划确定后续模块优先级、首个模块的最小范围及逐个上线条件。
- 公司研究标准继续以[研究方式](../../研究方式.md)为准。Skill 维护执行步骤和专用工具，最终结论、图表与验收记录写回该公司的唯一 HTML 主报告。
- 本轮规划排除批量改写公司报告、改造既有生成器、建设 MCP、发布市场，以及一次性封装全部十一项问题。已有 Excel、财报附件及历史 Markdown 按各自用途保留。

## 3. 现状分析

| 已有能力 | 能验证什么 | 下一步依赖 |
|---|---|---|
| [营收 Skill](../../研究流程/skills/revenue-analysis/SKILL.md) | 最终 HTML 中集团营收年度和单季覆盖、金额填列及表序 | 期间以开工所查披露为依据。分部口径、来源和解释仍需证据验收 |
| [估值反推 Skill](../../估值反推Skill/skills/implied-valuation/SKILL.md) | 正利润和未来 PE 模型适用时，复算支撑现价的利润、增速及延迟情景 | 行业、经营兑现路径及参数依据须另核。CoreWeave 等采用其他模型时，按 SOP 验收其模型和证据 |
| [报告工具](../../研究流程/tools/reports/reports.py)与[交付清单](../../研究流程/standards/研究更新与交付检查清单.md) | 索引和结构检查，另有资料、计算、图表、研究判断的验收要求 | 后续脚本应直接核对报告或对应输入，返回可定位缺口 |

本地 CoreWeave 专项核验 `CRWV/factcheck/full-report-audit.json` 已经能对报告中的盈利、CFO、现金 CapEx 和 FCF 做公司级对照，适合作为复用和回归的起点。[QXO 的验收记录](../../QXO/factcheck/sop_audit.json)呈现了另一类问题：费用及现金流可以勾稽，财报版本差异、异常税项归因和资本结构定价仍需要额外证据。

## 4. 设计与推进顺序

| 顺序 | 模块 | 第一版应抓的错误 | 证据验收重点 |
|---|---|---|---|
| **下一项** | **现金流与资本开支** | 年度或单季缺栏，FCF 算错，现金桥不闭合，表图数字与已核输入不一致 | 区分现金 CapEx、资产新增、租赁、预付与未付承诺。标明现金和受限现金口径，并解释投入如何影响现金回收 |
| 第二项 | 盈利与异常 | 利润率或利润桥算错，集团净利与归母利润混用，异常税费或非经营收益没有单列 | 核对附注和重述版本，逐项解释利润异常及正常化调整的依据与税效 |
| 第三项 | 融资、债务与稀释 | 债务到期表加总错误，融资额度当到账，回购授权当已执行，潜在股数复算错误 | 分开已发生和可能发生，明确追索、租赁、可转债及不同股类的边界，回写估值股数与资本结构 |
| 候选 | 客户与订单 | 将签约、RPO、ARR、收入、回款混为一谈，或把匿名客户写成实名 | 核对客户身份、合同阶段、取消条款、交付时点和来源。先试用证据表，再决定是否独立成 Skill |
| 候选 | 业务、竞争、治理与护城河 | 重要判断没有对应事实，跨公司对比口径不一致 | 继续按现有 SOP 和正文证据验收。积累具体重复缺陷后再决定如何拆分 |

现金流与资本开支排第一，因为已有可复算的公司资料，错误会同时影响资金用途图、融资判断和估值。第一版只覆盖 **CFO、现金 CapEx、FCF、期初到期末现金桥**。盈利正常化、完整债务模型和估值归因排在各自模块处理。图表检查在产生数字的模块执行，跨模块一致性保留在整篇交付清单。

## 5. 数据、接口与流程变更

建议沿用公司 `factcheck/` 数据和本地脚本。首个模块仅补充必要的核验输入：主体、期间、币种和单位、指标及口径、来源定位、误差依据、最终 HTML 的表格位置。使用报告已经声明的 FCF 口径；碰到公司调整后 FCF，分别验证公司披露和本 SOP 下的复算。现金桥纳入公司披露中的融资、投资、汇率等调整，期初与期末沿用同一现金范围。

脚本读取已核输入和最终 HTML，返回报告版本、预期与实际、差额、缺口及定位。可复算错误以非零退出。报告核验区记录这次采用的检查结果，以及需要人工判断的口径和证据。首期沿用现有报告索引、网页接入和 `research.yaml` 接口。

执行顺序为：根据用户任务定范围 → 确定期间和资料 → 执行适用 Skill → 写回 HTML → 对照原范围检查正文 → 修复并重跑 → 检查摘要、图表、估值和跟踪项是否同步。证据限制影响的条目单独留缺口和原因，交付结论与实际完成范围一致。

## 6. 实现步骤

1. **锁定回归样本。** 保存营收已知漏项及估值适用与不适用的案例。挑选 CoreWeave 和 QXO 现有现金流资料，记录正确底表和已知口径风险。
2. **实现现金流模块。** 编写短 Skill 和可复算脚本，接入 SOP 及现有交付清单。优先验证两家报告现有数据，在临时副本制造错误复验。
3. **以一次实际报告交付验证。** 分清脚本拦住的错误、研究证据确认的问题和仍未完成的事项。若漏报或误报，先修正模块并重跑原样本。
4. **验收通过后才启动下一项。** 从列表中选一个模块，用同样方法定义错误样本和完成条件。实际高频缺陷变化时可调整顺序。

## 7. 风险与处理

- **范围被悄悄缩小。** 开工记录用户任务类型及应覆盖范围，交付检查沿用该记录。新增财报不能自动把主报告迁移变成财报专题。
- **脚本过度相信分类。** 同一份错误输入可以让图表与计算一起对上。现金 CapEx、租赁和受限现金仍逐项对原始披露，脚本通过与口径核验分别记录。
- **历史数据不可比。** 对主体变化、重述、未披露或获取失败分别标明已查资料、影响及后续条件。用真实差额与披露精度判断舍入，避免用宽容差隐藏缺口。
- **增加上下文和重复维护。** SOP 保有内容规则，Skill 放流程和检查，报告核验区保有结果。已有脚本仅在可推广、口径一致时提取共享逻辑。

## 8. 验证与进入下一模块的条件

| 样本 | 预期结果 |
|---|---|
| CoreWeave 和 QXO 的已核现金流数据 | 对原期间正确复算 FCF，现金桥在对应披露精度内勾稽，报告表格可定位 |
| 临时副本删一季、改错 FCF、漏列桥接项 | 脚本逐项指明主体、期间、指标、位置或差额，并返回失败 |
| 临时样本将资产新增或未付承诺作为现金 CapEx | 已标记的口径冲突能被检查发现。无法从数字识别的情况由原始证据复核给出结论 |
| 一次实际报告采用新模块 | 原任务范围、最终 HTML、图表、估值与核验记录相互一致，关键缺口有明确交付状态 |

四类验证均有记录、可修复错误已复验，才进入下一模块。后续评估以已知漏项检出、合规样本通过和实际交付一致性为准。

## 9. 回滚方案

每个模块独立提交。若在试点出现误报或无法兼容披露形式，回退该模块的 SOP 挂接和本地安装版本，恢复原有人工清单和核验步骤。保留原始证据、报告正文、历史核验记录及回归样本，待修正后重新验证。已工作的营收和估值模块独立保留。

## 10. 待确认问题

- 建议第三个 Skill 先做现金流与资本开支，第一版仅验收 CFO、现金 CapEx、FCF 和现金桥。请确认这一优先级和范围。
- 建议用 CoreWeave 与 QXO 作为首轮样本，随后在一次实际报告交付中验证，达到条件后才开始盈利与异常模块。

按工作区方案门禁，审阅确认后进入第一项实施。
