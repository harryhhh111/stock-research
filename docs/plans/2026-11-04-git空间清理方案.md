## 设计方案

优先采用默认过期策略的 Git 垃圾回收，不使用 `--prune=now`，不执行 `reflog expire` 或 `filter-repo`。预计可以释放约 4.5–4.9 GiB，最终以磁盘实测为准。

Git 官方说明：默认过期时间两周；立即 prune 与并发写入存在损坏风险；cruft pack 会保留未过期的不可达对象。

参考：https://git-scm.com/docs/git-gc 、https://git-scm.com/docs/git-repack （经 Context7 核对）。

## 数据模型 / API / 流程变更

无研究数据模型或 API 变更。只重组 Git 对象存储并移除符合过期条件的不可达对象；所有保留引用的提交 ID 应保持一致。

## 实现步骤

1. 在无其他研究任务、Git 写入、自动检查点或维护进程的窗口执行。执行前重新核验 refs/reflog 可达集合，不能沿用本快照直接删除。
2. 记录 refs、HEAD、reflog、索引校验、工作区状态和待保留文件清单/校验。完整运行 `git fsck --full` 并确认没有对象完整性错误；dangling/unreachable 本身不是损坏。
3. 将完整 `.git` 复制到工作区外的独立备份目录，验证复制完整性及可读取性。普通 bundle 不包含全部无引用对象，不能替代此备份。备份约需 5 GiB；同盘备份只转移占用，最终释放本机空间需迁出或在验收后另行批准删除备份。
4. 在停止并发写入后运行 `git -c gc.autoDetach=false gc`，保留默认 prune 宽限期与 reflog 默认保留策略，不用 aggressive/force。
5. 若 249 MiB 临时对象仍存在，核实没有进程持有、备份中存在且 Git 完整性通过后，将这个明确路径的文件移到仓库外备份目录。不得通配符删除整个 objects 子目录。
6. 如回收不充分，重新分析 cruft、保留根及过期策略；不得自行升级为立即 prune、删除 refs 或过期 reflog。

## 风险点

- 并发写入会改变可达性并带来清理竞争；必须停写。
- 不可达对象可能包含旧的未提交工作，只能通过完整备份保留恢复能力。
- 当前存在大量未提交修改及未跟踪文件，不得 reset、clean、stash 或重新克隆替换工作区。
- 备份及重打包需要额外空间，开始前再次检查空间；备份失败即停止。
- 现有 Codex 检查点可能继续变化，实施前后必须重新比较。

## 验证方式

清理后再次运行 `git fsck --full`、`git count-objects -vH`、`du`；比较 refs 和 HEAD 提交 ID、索引、工作区文件校验及状态，要求研究内容不变（本方案文件等已知新增文档除外）。确认原始行情仍在、现有检查点和 reflog 可读取。记录实际释放量及备份占用，不把迁出仓库的同盘备份计为磁盘净释放。

## 回滚方案

若完整性或内容核验异常，立即停写，保留清理后的 `.git` 作为诊断副本，从完整备份恢复 `.git`，再核验 refs、索引及工作区。恢复期间禁止其他任务写入；工作区研究文件不覆盖。备份至少保留到验收完成，删除备份另行确认。
