# 微软报告结构与模块化研究Skill调整方案

日期：2026-11-14；状态：待用户审核。本轮只读取现有规范、HTML图形生成逻辑及skill-creator规范，创建本方案；未修改研究报告、SOP或安装skill。

## 1. 背景与目标

用户认可HTML和桑基图，但指出当前按十一项机械排列，造成业务解释与营收分离、指引位置靠后、图形过多、资本分配与利润现金链路断开，治理与核心矛盾混放。单纯继续加SOP条款也不足以保证估值等高投入研究真正执行。

目标：先让初中生听懂公司如何赚钱，再用财务验证；让最新实绩与下一期指引靠前且边界清楚；按研究问题选择简洁图形；用按需加载的模块化skill组织取证、计算、解释与验收。

## 2. 范围与非目标

范围：MSFT/MSFT.html及配套图形/检查脚本；研究方式、主文档模板、HTML展示规范和检查清单的相关条款；新增公司研究入口skill与估值skill及必要模块参考。

非目标：不刷新所有财报/行情、不批量重构其他公司、不删除历史Markdown、不维护双份正文、不调整证券入口schema、不预设新增完整估值已完成、不把skill安装等同研究质量保证。用户本次“你看看”按结构审阅处理，审核后再实施。

## 3. 现状分析

当前HTML保留十一项标题及云AI专题，采用10组图形，业务说明、营收表、分部调整和应用边界散布多处。新增收入瀑布图混入大额期初/期末收入，增量差异被压缩。最新指引在2.4节，位于长历史表之后。分红与资本分配远在第8节。估值虽有反推，仍存在正常化盈利、资本投入桥、同业与历史可比底表等研究缺口。

现SOP硬性要求十一项作为一级模块；本次不能只改微软HTML标题而让规范继续冲突。建议把“十一项必须覆盖”和“十一项必须分别作为h2”拆开：前者保留，后者改为允许合并重排，并在验收中显式映射内容位置。

## 4. 报告设计

### 4.1 建议阅读目录

摘要先回答：怎样赚钱、核心矛盾、当前判断、正反证据；随后列研究状态、数据截止与目录。

| 新阅读模块 | 内容与组织 |
|---|---|
| 1. 微软怎样赚钱 | 先用白话逐项解释产品、付款方、购买理由、收费方式；每项紧跟收入规模/占比及可得利润证据。用链接定位第2节完整表，不重复复制大表 |
| 2. 赚了多少，钱怎样分配 | 开头展示最新单季实绩与下一季指引，随后三年营收、业务增长贡献、收入利润桑基图；图下紧接分红/回购/再投入的摘要和跨第3节定位 |
| 3. 利润变成多少现金，投入能否回本 | 利润→CFO→FCF，现金来源用途、现金CapEx、租赁、分红回购实绩、股数、并购投资、现金债务与到期；承诺与已付区分。接续第2节，承接原第3和第8节完整内容 |
| 4. 客户与需求 | 真实付费链路、实名采用案例、集中度、用量、续费及客户资金来源 |
| 5. 竞争对手 | 逐业务匹配，产品/价格/成本/份额证据及可比限制 |
| 6. 行业景气 | 需求、供给、价格、库存、电力与设备约束；与公司影响相连 |
| 7. 订单与投入兑现 | RPO期限/条件、容量交付、收入确认与收款；不把订单当现金 |
| 8. 估值与资金效率 | 正常化利润、估值口径、现金回报、历史同业、反推情景、敏感性及反证；不能只报PE |
| 9. 治理与文化 | 控制权、董事会、激励、资本配置纪律、安全/合规、组织文化的行为证据与反证 |
| 10. 护城河 | 按业务说明来源、证据、趋势与侵蚀者 |

末尾保留主要风险、跟踪指标、研究缺口、核验与来源。云与AI是用户指定重点，保留专题定位；重复财务表改为回链，专题保留独有机制和口径说明。

**核心矛盾不再与治理并列一个模块**：放到摘要前置，并在相关经营/估值章节补证据；治理与文化是独立模块。合并后的标题数不必等于原十一项，但任何必需内容都不能因改标题而丢失。

### 4.2 “给初中生解释”落实方式

每项重要业务固定回答四个自然问题，不把术语当解释：

1. 它卖什么？用一个具体任务说明。
2. 谁为什么愿意付钱？讲清付款者和使用者是否相同。
3. 怎么收费、钱记到哪里？授权、订阅、资源消耗和广告分开。
4. 这块有多大、利润来自哪里？紧贴金额/占比；没有独立利润须明说。

例如SQL Server：“公司要记录订单、库存和客户资料，需要一个管理这些资料的软件。企业向微软买使用权，可以自己安装在服务器上；微软卖的是数据库软件许可。若企业改用微软托管的云数据库，则还在为持续运行服务付费。”这是机制示意；实名客户采用案例另列，不能用假想例子冒充事实。

Azure：“企业租微软机房里的计算、存储等能力，按用量或合同付费”；M365：“企业为员工购买办公与协作工具，再为更多功能或AI升级付费”。先中文解释，再给产品名称与术语；“容易理解”不代表省略授权和云、集团和业务的边界。

### 4.3 最新实绩与指引前置且放进图表

第2节开头设“现在表现怎样，接下来怎么看”，展示四列：上年同季、最新实绩、下一季指引、指引对应上年同季基数。必要的完整季度表放下方，不能为了前置只保留最新一期。

- 实绩柱用实心，预测用虚线边框/区间条并写“公司指引”；指引发布日期、期间、数值/定性说法、汇率和一次性假设常驻图表附近。
- 不用折线把全年、季度、TTM和指引连成同一连续实绩。集团收入金额、Azure固定汇率增速、云毛利率分别作为不同量纲的小图或表行。
- 公司不给金额时不强造金额；无分部指引写未给。区间不擅自取中点当官方预测；若自行取中点须标复算。
- 非常重要的季度历史仍全部展开，三年年度表与年内季度表分开。与当前SOP“指引单列”的冲突改为“同表可分组呈现，但必须明确隔离预测与实绩”，不取消口径纪律。

### 4.4 图表逐项调整

| 当前图 | 调整 | 理由/条件 |
|---|---|---|
| 新增收入瀑布：281.724→331.839 | 改为“一个有正负方向的堆叠条”，右侧生产力+19.186与智能云+31.526，左侧个人计算−0.597，醒目标净增50.115 | 只画增量，不用大额存量挤压变化。含负贡献，不画普通饼图；零线、正负金额同尺度 |
| 收入利润、现金来源用途桑基图 | 保留并安排前后接续 | 用户已认可，适合解释来源和分配；仍然分图，不跨会计口径连线 |
| RPO未来12月/之后分配 | 可用单根100%堆叠柱或环形图，标总额677及约30%/70% | 两项同口径、非负、覆盖完整总额，适合构成图；必须标预计确认而非收款 |
| 已列现金用途 | 单根堆叠柱或饼图仅在分母清楚时采用 | 可列“本图三项用途合计”，不可冒充全部现金付款；有净流入/负数不强画饼 |
| 净利润→CFO调节桥 | 保留瀑布图 | 有正负调节与起终点，饼图会破坏含义；无需将所有瀑布都替换 |
| 三年CFO/CapEx/FCF及利润率 | 保留适用趋势图，减少重复 | 金额与比率分图，FCF是差额而非第三项构成用途 |

这是对已批准“桑基图优先、瀑布图兜底”的细化：该优先级用于流向/变化问题；同一时点构成允许饼图/单柱，趋势仍用趋势图，不机械强套。

### 4.5 分红与资本分配前移

收入利润桑基图下立刻回答“赚到的钱，如何再投入和回报股东”，放简明摘要及第3节现金图链接；第3节紧接展示实际付款、租赁、分红回购及股数等完整数据。保留醒目一句：分红、回购和现金CapEx不是利润表费用，不能直接从营业利润桑基图扣除。原第8节必要内容全部映射到第2/3节，只保留一份主要底表。

## 5. 研究Skill设计

### 5.1 SOP与skill职责

SOP继续作为研究最低标准与证据纪律的唯一入口；skill负责选择任务模式、实际取证、计算、分析和交付检查，引用SOP，不复制一整套可能分叉的标准。模板负责阅读结构。skill不能靠命令“必须深入”保证质量，必须要求可检查的产出和未通过状态。

推荐先做两个skill，而不是一开始安装十一个互相调用的skill：

- `company-research`：处理公司研究、局部业务专题、更新与重构，按需要读取业务、财务、客户竞争、治理文化、图表交付模块参考；不是通用软件开发或所有股票新闻的入口。
- `stock-valuation`：可独立处理“现在贵不贵、包含什么预期、怎样估值”等问题，也供公司研究流程使用。估值查询不被简化成只拉行情算PE。

模块先用按需加载的references，避免每个任务都加载全套研究细节。某模块经反复使用证明需要独立调用，再拆成单独skill。默认可自动发现，不额外设置每次审批或主动多代理流程。

新skill建议按skill-creator默认位置安装到`~/.codex/skills/company-research/`、`~/.codex/skills/stock-valuation/`；详细工作区规则保留仓库内，引用时先定位适用工作区，不能把本机绝对路径写成所有环境通用规则。安装前审核本方案，实施时再创建文件。

### 5.2 估值模块的执行门槛

| 阶段 | 必需产出与检查 |
|---|---|
| 对象与期间 | 证券/股类/币种、真实行情时间、可用股数、最新财报与TTM、期后融资/收购；无法核对不得称实时估值 |
| 盈利正常化 | GAAP到调整口径的逐项桥，现金/非现金、税前/税后、经常/一次性，股数与SBC；公司non-GAAP不默认等于核心利润 |
| 财务与资本回报 | CFO/CapEx/FCF、租赁及债务、投资与承诺，ROE/ROIC适用性；不能拿现金投入前利润替代可分配现金 |
| 估值方法 | 根据业务/阶段选适用方法并解释；成熟盈利、亏损成长、金融/周期、分部估值分别选口径，不强制凑两个模型 |
| 比较与反推 | 同口径历史/同业可比性、价格隐含经营假设、要求回报率与终值敏感性；假设不称市场共识 |
| 结果与反证 | 哪些假设支持价格、怎样证伪、安全边际来自哪里；未知关键输入保留缺口，不机械给买卖评级 |
| 交付与验收 | HTML及同源计算输入/输出/公式、相关摘要与跟踪更新；实际完成和关键未完成分别记录 |

不以固定耗时或篇幅作质量标准；关键输入与反推没有做到，即使PE计算正确也不能标完整估值研究完成。局部提问按问题选阶段，但必须说明分析范围，不能用“局部”规避决定结论的关键限制。

### 5.3 治理与文化模块

检查控制权/投票权、董事会监督、激励指标、关联交易、资本配置、安全合规，以及组织行为如何影响业务执行。文化须给可核实的制度、资源配置、事故整改、产品/客户行为证据及反证；区分管理层自述、外部评价与研究者判断，不从口号或股价涨跌推导优秀文化。

## 6. 数据模型/API/流程变更

不改证券身份或入口schema；HTML继续唯一维护正文，原入口工具限制如实保留。图表/表格增加实绩或指引状态、预测目标期间、发布日期、范围、汇率假设等必要元数据，指引与实绩可邻接但不可混标。

内容映射保存为主报告核验章节中的迁移记录，不另建第二份公司正文。各模块取证/计算可复用现有数据和脚本；skill脚本只在能可靠重复计算或验证时增加，不先造一套大框架。

## 7. 实现步骤

用户批准后：

1. 同步调整SOP“十一项内容覆盖”与可合并阅读结构、指引邻接展示规则，模板/清单/展示附件一致。
2. 创建两个skill及必要模块参考，做命名/frontmatter/引用检查和真实任务行为验证，不把格式验证称为研究质量通过。
3. 以微软作为首个试点：重写白话业务解释，调整第1/2节，前置指引，重排资本分配、核心矛盾与治理文化。
4. 替换增量图、简化RPO构成图，保留适用桑基及变化桥；修正图形生成器、目录和检查脚本，不让旧固定11个h2的断言阻止新阅读结构。
5. 按估值skill识别微软关键缺口。若未实际补全底表，保留未完成；本次结构改造不伪装已重做完整估值。
6. 内容保留映射、金额与期间勾稽、来源、桌面/窄屏/打印及离线验收，报告实际通过项与限制。

## 8. 风险点与验证方式

- 口语化丢精度：检查付款方、确认方式、并表边界、授权/云/SaaS区分，术语解释靠具体交易，真实客户案例不能省略。
- 指引混入实绩：检查图例、样式、期间、日期、汇率和同比基数，不将定性指引精确化。
- 图形简化隐藏负数：核对增量+19.186+31.526−0.597＝50.115；饼图只用于合格构成，不用绝对值凑100%。
- 结构调整丢解释：逐项检查分部重划、Windows/SQL归属、投资利润桥、租赁分类、FCF、估值假设等旧追问位置。
- Skill只变成更长SOP：检查是否实际产生原始证据、计算和结论，是否按需加载，是否只修改本次授权内容；选择真实估值提问与治理文化任务验证输出。
- 规范与报告冲突：旧十一项每项须有新定位，三完整年和当年完整季度不因重排删除。技能格式检查与财务/内容/视觉验收分开。

## 9. 回滚方案

按本轮差异回退HTML、图形脚本、验证脚本和四份规范，避免覆盖同期用户改动。新skill单独回退新增文件；旧研究Markdown、原始证据与证券身份不改，不全库重置，不自动删除历史文件。

## 10. 待确认问题

建议整体批准上述阅读结构、图形规则和“两skill＋按需模块参考”的实现方向。若用户只希望先改微软，可先实施报告试点，再推广到SOP和skill；在明确审核前不创建skill或修改正文。
