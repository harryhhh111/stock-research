## 样本与方法

从本机可读取的 `~/.codex/sessions/**/*.jsonl` 中筛选 session_meta.cwd 为本研究工作区的记录，提取 response_item 中 role=user 的文本，按消息 ID 去重，排除环境、页面、插件列表、自动 heartbeat 和审批 transcript 等系统注入。

得到 **34 个聊天、668 条人工输入**，上海时间范围为 **2026-08-20 至 2026-10-08**。包括问题、追问、纠正、操作指令、确认和用户粘贴的其他回答，不能等同于 668 个独立问题。没有覆盖所有归档、已删除、远程或其他项目聊天。相同文字在不同消息中保留。

全量检索发现模式，人工检查代表性追问、抱怨与当前规范。不将历史回答当作金融事实来源，也不仅凭用户抱怨认定原回答必然错误。以下日期为上海时间，引用仅作为用户需求证据。

## 核心判断

研究正在从认识公司，走向解释经营变化、判断价格隐含预期和持续跟踪。现有 SOP 有主题清单，但缺少最低交付标准和完成检查。用户反复充当检查人：补历史、补比率、补业务边界、要求解释、要求落盘或合并。

应区分四类输入：返工型（原任务漏项）、深入型（新的投资问题）、动态型（新消息/行情）、理解型（术语与机制）。不能把所有追问都判为 SOP 失败。

## 重复模式与需要补的标准

| 估值没有含义 | Intel 当前价格说明什么；SNDK 要维持怎样增长；腾讯被当成什么公司估值 | 倍数外加历史与同业对比、周期位置、价格隐含情景、假设与失效条件；反推只是模型结果，不宣称代表全体市场观点 |

| 比较口径与证据不稳 | 固定模型 token 价格 vs 混合均价；同资金机柜比较；SSD 涨价多口径 | 先明确对象、期间、单位、分母和范围；来源、公式可追溯；事实、指引、第三方估计、自身推演分开；冲突证据并列 |
| 文档碎片化 | INTC、META、MU、三星、NVDA、SSD、DeepSeek、PDD、JD 多次要求合并 | 默认一份公司主文档，必需分析模块作为章节；用户要求或独立专题确有复用价值再拆。研究结论回写主文档，数据与复算保留 factcheck |
| 长度和解释失衡 | 腾讯先说不细致，随后说太长；术语和商户收费没懂 | 先直接回答，再给紧凑表格与关键说明；详细的是机制和证据，避免百科堆积；首次术语简释并补术语表 |
| 状态与动态缺入口 | “研究过吗”“忘记怎么推进”“最近有什么消息” | 公司索引、研究状态、待验证问题、关注名单、数据截止日与更新记录；新闻/行情由持续采集承接。个股/主题异动先核对时间，候选解释不当因果 |
| 资料没有收敛成判断 | 研究两个月仍不知如何判断是否买；反复问贵不贵 | 当前观点、关键假设、正反证据、跟踪指标、下一条能改变判断的信息。资料完整不自动等于买入结论 |

## “至少三年”不能只变成下载三份财报

应交付三完整财年可比底表、最新增量及上年同期、已披露分部历史、同比和利润率、变化解释、来源与复算。历史长度不仅用于营收，也用于利润、现金流、资本开支和资金效率。

信息确实缺失时说明已查来源、披露边界、替代信息与不可比原因，不能反复留下无解释的“待核验”。非上市公司、退市公司、近期分拆公司的资料不保证齐全。

腾讯追问“利率”结合上下文可能指利润率，不应直接判为债务融资利率；融资成本另按债务披露分析。

## 现有 SOP 的实际冲突

- 《研究方式.md》2026-09-15 版本已加入护城河，并要求过去 3–5 年的壁垒变化，部分历史反馈已经吸收；但财务三年、同比与利润率没有普遍最低标准。
- “固定主线 6 篇每家公司必走”与后来多次明确“一份主文档、要求后再拆”冲突，应将文件数量与必需模块分开。
- 文内仍称“九问”，实际十一项；AGENTS 仍写九步框架，也应保持一致。
- 研究方式引用 stock-research 技能，但在本次查找的 `~/.agents/skills` 与 `~/.codex/skills` 未找到。其他环境是否有，尚未核实。关键标准不应只藏在远程无法访问的个人技能中。

建议用现有两份文件承担明确职责：研究方式是流程和验收唯一入口，AGENTS 是执行约束并引用它。暂不另建多个 SOP，后续可选检查工具沿用相同标准。

## GitHub 同步判断

GitHub 不是云服务器读取研究的必要条件，受控文件同步或上传接口也可以。对 Markdown 为主的研究库，独立私有 GitHub 仓库是合适的版本化渠道；研究与网站代码继续分仓。

现状：本地已初始化 Git，`git remote -v` 没有输出；大量修改、删除和新文件未提交。当前 ignore 主要排除缓存、虚拟环境和参考嵌套仓库，没有排除大体积行情数据。工作目录可见约 400 MiB 的 npz 和超过 100 MiB 的分钟行情 JSON。尚未审计完整 Git 历史的大对象及敏感内容，因此不能直接全部 add/commit/push。

建议上传研究 Markdown、SOP、必要小附件、复算脚本与数据来源说明；大体积行情、逐笔 ZIP、可重建数据和数据库另存，保留获取方法。服务器只读拉取研究版本，再做增量索引。push 本身不会自动使网站显示内容，仍需拉取、解析、公司映射、页面和访问权限。GitHub 私有仓库与网站内容访问权限分别控制。

[GitHub 文件限制](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)：普通 Git 阻止超过 100 MiB 的文件；[Deploy keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys) 可限定单仓库访问，默认只读。本轮通过 Context7 和官方页面核对。

## 建议先解决的三个返工源

1. 三完整财年及最新增量期间。
2. 同比、比率与经营变化解释。
3. 默认一个主文档，重要业务讲透。

再补估值含义、证据口径和完成检查。研究同步和每日跟踪作为网站接入议题另行推进，不必等待所有历史研究补齐，也不能以上传代替研究质量控制。

本轮仅分析，未执行 SOP 修订、GitHub 创建/推送或网站改动。
